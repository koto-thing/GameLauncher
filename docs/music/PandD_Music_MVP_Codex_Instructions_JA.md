# PandD Music 初期版（MVP）実装指示書

## 0. Codexへの依頼

PandDサークルのゲーム内で使用したOSTを、学外の人も自由に楽しめる音楽配信Webサイトとして実装してください。
サービス名は **PandD Music** です。Nintendo Musicに近い「作品の世界観を感じながらゲーム音楽を聴く体験」を参考にしますが、ロゴ、画像、UI素材、ブランド表現を複製する依頼ではありません。

**設計案の提出だけで終わらず、フロントエンド、API、永続化、投稿・公開、再生、テスト、セットアップ手順まで実装してください。**

まず対象ワークスペースの `AGENTS.md`、README、既存コード、依存関係、実行・デプロイ方法、未コミットの変更を確認してください。ユーザーの作業を上書きせず、既存プロジェクトがある場合は尊重してください。対象リポジトリ名は指定されていません。GameLauncherのリポジトリが対象だと勝手に決めないでください。

優先順位は以下です。

1. 初期版の主要導線が実際に動くこと。特にスマホ再生、区間ループ、担当者による登録・公開。
2. 認証・作品単位の認可・非公開データの保護・データ整合性。
3. クリーンアーキテクチャ、調整値の集約、コメント規則、テスト。
4. 見た目の仕上げと、運営・引き継ぎのしやすさ。

この順序は、下位の項目を省略してよいという意味ではありません。最初の完成を妨げる過剰な機能追加を避けてください。未指定の軽微な仕様は本書の標準案で進め、採用理由を記録してください。本番の認証情報がない場合はローカル実装とテストを進め、実際に接続できていない箇所を正直に報告してください。

## 1. 確定している製品方針

| 項目 | 初期版で実装すること |
|---|---|
| 公開範囲 | 学外の人も利用できる一般公開。聴取は無料・ログイン不要 |
| 初回登録目標 | 2作品・合計5〜10曲程度。登録件数の上限ではない |
| 対象端末 | スマートフォン優先。PCでも利用可能 |

| 公開 | 担当者の判断で公開・更新・非公開化。運営の事前承認は不要 |
| 広告 | 広告枠を設け、運営が掲載の有効・無効を管理できる |
| 運営 | 作品・担当者・広告設定・公開停止などを管理できる |

**今回は実装しないもの**

投げ銭・決済・支援ページ・支援ボタン、動画、GameLauncher側の変更や連携、一般リスナーの会員登録、個人プレイリスト、お気に入りのクラウド同期、オフライン配信、ネイティブアプリ、コメント・評価、推薦エンジン、有料限定曲、複数ループ区間、リスナーによる独自A–B区間指定、15分・30分などの長さ指定は対象外です。

将来の投げ銭はサイト全体の運営費として受け取り、作曲者・作品ごとには分配しません。ただし、今回は決済SDK、決済テーブル、Webhook、残高管理、非表示の支援画面まで先回りして作らないでください。将来対応事項として文書に記録するだけで十分です。

## 2. 技術構成の標準案と前提

ホスティング、認証プロバイダ、フレームワークは、ユーザーが確定した事項ではありません。以下は**新規実装時の標準案**です。既存の適切な構成がある場合は、不必要に移行せず、本書の要件を満たす方法を採ってください。

| 分野 | 新規実装時の標準案 |
|---|---|
| 言語 | TypeScript。strict設定を有効化 |
| フロントエンド | React + Vite。ルーティングライブラリは既存構成を優先 |
| API | Cloudflare Workers。必要ならHonoなどの軽量ルーター |
| 静的ファイル | Workers Static Assets |
| DB | Cloudflare D1 |
| 音源・画像 | Cloudflare R2の非公開バケット |
| 投稿者認証 | GitHub OAuth。サイト内権限は別途DBで管理 |
| テスト | 純粋ロジックの単体テスト、DB/API統合テスト、ブラウザーE2E |

CloudflareのViteプラグインはWorkers・静的アセット等を扱う構成を提供しています。[R1]
Node.jsや各パッケージは実装時点で互換性を確認し、サポートされている版を選び、lockfileで固定してください。「latestなら何でもよい」としないでください。

低コストを優先しますが、無料枠で永久に運用できると断定しないでください。Workers・D1・R2の上限、操作回数、保存量、費用条件を公式資料で確認し、見積もりの前提をREADMEに残してください。[R8][R9][R10]
有料プラン契約、外部サービス課金、本番リソース削除、DNS変更、本番公開を勝手に行わず、まずローカル実行と再現可能なデプロイ準備まで完成させてください。

## 3. コード設計：クリーンアーキテクチャ

### 3.1 依存関係

依存方向は基本的に以下です。

```text
Presentation ──→ Application ──→ Domain
Infrastructure ──→ ApplicationのPort / Domainの型
Composition Root ──→ 各層を生成して接続
```

DomainはReact、HTTP、Cloudflare、DB、OAuth、Web Audio API、ブラウザーのグローバル変数、環境変数に依存させません。
Applicationは外部処理をPort経由で扱い、Infrastructureの具象クラスを直接生成しません。
UIのクリックハンドラーやAPIルーターに、権限判定・公開ルール・ループ計算・SQL・R2操作を詰め込まないでください。

API側の認可を必ず実行し、同じドメインルールをUIが再利用していても、それをサーバー検証の代わりにしないでください。

### 3.2 ディレクトリ例

```text
src/
  domain/
    entities/
    value-objects/
    policies/
    errors/
  application/
    use-cases/
    ports/
    dto/
  infrastructure/
    persistence/
    storage/
    auth/
    audio/
  presentation/
    web/
      pages/
      components/
      hooks/
    api/
  composition/
    client.ts
    server.ts
  config/
    domain-policy.defaults.ts
    player-runtime.defaults.ts
    server-config.ts
    design-tokens.css
migrations/
tests/
  unit/
  integration/
  e2e/
scripts/
docs/
```

この構造の名前に合わせるためだけに既存コードを大移動しないでください。役割と依存方向が守られていれば、機能単位のディレクトリ構成でも構いません。クライアントのbundleにサーバー用の設定や認証実装を混入させないでください。

### 3.3 主なモデルとPort

ドメインの候補は、`Game`、`Track`、`TrackRevision`、`TrackCredit`、`LoopRegion`、`PublicationState`、`GameMembership`、`PlaybackState`、`PlaybackQueue`です。

必要な外部境界だけをPort化してください。例：

- `GameRepository` / `TrackRepository` / `MembershipRepository`
- `AssetStorage` / `IdentityProvider` / `SessionStore`
- `AudioEngine` / `Clock` / `RandomSource`

SQLの詳細、Web AudioのNode、OAuthのレスポンスを、そのままドメインの公開APIに流し込まないでください。日時・乱数・音声エンジンはテストで差し替えられるようにします。

単にクラスを増やすことが目的ではありません。不要な汎用Repository、独自DIフレームワーク、マイクロサービス、イベントソーシング、汎用CMS、巨大な共通Utilityは作らないでください。Composition Rootでの明示的な依存注入で十分です。

## 4. 調整値を変更しやすくする設計

### 4.1 調整値の置き場所

「ドメインの値を変更すればパラメータを容易に調整できる」設計にしてください。ただし、秘密情報や画面の余白まで無差別にDomainへ入れることは避けます。

| 種類 | 置き場所・変更方法 |
|---|---|
| 業務ルール | 型付きDomain Policy。初期値を1か所に集約し、Use Caseへ注入 |
| 曲固有の値 | DB。曲順、画像、クレジット、ループ開始・終了などを管理画面で変更 |
| サイト運営設定 | DB。広告の有効・無効、運営バナーなど |
| 音声エンジンの技術設定 | 型付きRuntime Config。メモリ予算、試聴の先行秒数など |
| UIの見た目 | CSS変数などのDesign Tokens |
| 秘密・環境固有値 | サーバー側環境変数・Secret。クライアントに公開しない |

型の契約と業務的な検証をDomainに置き、設定値の読み込みは外側で行って注入してください。ドメイン層から `process.env` やCloudflare Bindingを直接参照しないでください。

### 4.2 初期調整値の例

以下は調整可能な初期案です。測定結果に基づいて変更してよいですが、採用値と理由を記録してください。

```ts
// domain-policy.defaults.ts
// 投稿可能な素材とループ区間の業務ルールを一元化する。
export const DOMAIN_POLICY_DEFAULTS = {
  media: {
    maxAudioFileBytes: 64 * 1024 * 1024,
    maxImageFileBytes: 8 * 1024 * 1024,
    maxAudioDurationSeconds: 600,
    maxImageEdgePixels: 4096,
  },
  loop: {
    minimumLengthSeconds: 0.1,
  },
} as const;

// player-runtime.defaults.ts
// ブラウザー側の音声処理の負荷と編集時の使い勝手を調整する。
export const PLAYER_RUNTIME_DEFAULTS = {
  decodedAudioBudgetBytes: 96 * 1024 * 1024,
  simultaneousDecodeLimit: 1,
  loopPreviewLeadInSeconds: 3,
  nextTrackAudioPrefetchEnabled: false,
} as const;
```

デコード後の予算は「全端末で安全なメモリ量」の保証ではありません。圧縮音源や作業用バッファを含めたピーク負荷も測定します。
通常再生できる曲でも、区間ループ用のデコード予算を超える場合があります。その場合は投稿者に理由を表示し、対応する音源への差し替えか通常再生のみを選べるようにします。公開後に黙って区間ループ機能を無視しないでください。

秒、ミリ秒、サンプル、byte、pixelを混同しないように、型や名前で単位を明示してください。不正な設定値は起動時または保存時に検出します。
設定の初期値を変更しただけで、既存曲のループ地点や公開状態が勝手に書き換わらないようにしてください。
重要な認可条件や秘密情報を、一般投稿者が編集できるパラメータにしないでください。

`docs/parameter-guide.md` に「何を変えると、何が変わるか」「反映に再起動・再デプロイが必要か」をまとめてください。

## 5. コードコメント規則【必須】

### 5.1 処理ブロックのコメント

TypeScript / JavaScriptは、**意味のある処理ブロックごとに `//` コメント**を付けてください。
入力検証、認可、データ取得、状態遷移、副作用、エラー処理、クリーンアップ等のまとまりごとに、目的・理由・注意点を日本語で説明します。

`// if文`、`// データを取得`など、構文や直後の関数名を言い換えるだけのコメントを量産しないでください。なぜその順序か、何を防ぐか、どういう前提かを書いてください。

JSX内は `{/* ... */}`、CSSは `/* ... */`、SQLは `--` など、その言語で有効な構文を使用します。`//` を無理に使って構文エラーや画面への文字表示を起こさないでください。

### 5.2 関数のコメント

**自作の関数・メソッド・コンストラクター・Reactコンポーネント・カスタムHookに、Doxygen風の `/** ... */` ドキュメントコメント**を付けてください。
基本タグは `@brief`、`@param`、`@returns`、必要な場合は `@throws` / `@remarks` とします。存在しない引数・戻り値・例外の説明を機械的に付けないでください。

副作用、単位、認可の前提、再生状態の変更、呼び出し順の制約など、利用者が知る必要のある情報を記載します。匿名コールバックにも説明を付け、複雑なものは名前付き関数へ抽出してください。
テストヘルパーや運用スクリプトにも適用します。外部依存・自動生成コードは対象外です。
TypeScript向けのJSDocとして扱い、コメントのためだけにC++向けDoxygenのビルド環境を追加する必要はありません。

### 5.3 コメント例

以下は形式を示す例です。実装ではドメインの型・エラー設計に合わせてください。

```ts
/**
 * @brief 再生対象の音源長とルールに基づき、有効な区間ループを生成する。
 * @param startSeconds ループ開始位置。音源先頭からの秒数。
 * @param endSeconds ループ終了位置。音源先頭からの秒数。
 * @param durationSeconds 検証済みの音源長。秒単位。
 * @param minimumLengthSeconds 許容する最短ループ長。秒単位。
 * @returns 開始・終了位置が不変のループ区間。
 * @throws RangeError 値が有限でない場合、または許容範囲外の場合。
 */
export function createLoopRegion(
  startSeconds: number,
  endSeconds: number,
  durationSeconds: number,
  minimumLengthSeconds: number,
): Readonly<{ startSeconds: number; endSeconds: number }> {
  // NaNやInfinityが比較処理をすり抜け、再生状態を壊すことを防ぐ。
  const values = [startSeconds, endSeconds, durationSeconds, minimumLengthSeconds];
  if (!values.every(Number.isFinite)) {
    throw new RangeError("ループ設定には有限の数値を指定してください。");
  }

  // 最低ループ長を含む業務ルールを、UIの入力制限とは独立して検証する。
  if (
    durationSeconds <= 0 ||
    minimumLengthSeconds <= 0 ||
    startSeconds < 0 ||
    endSeconds <= startSeconds ||
    endSeconds > durationSeconds ||
    endSeconds - startSeconds < minimumLengthSeconds
  ) {
    throw new RangeError("ループ区間が許容範囲外です。");
  }

  // 検証後に呼び出し元から値を書き換えられないよう、不変の値を返す。
  return Object.freeze({ startSeconds, endSeconds });
}
```

コメント方針を `docs/comment-guidelines.md` に保存し、追加コードで継続できるようにしてください。

## 6. リスナー向け画面と基本再生

### 6.1 画面

**ホーム**：作品一覧、作品画像、作品名、簡単な説明、作品ページへの入口、広告枠。2作品でも寂しくなりすぎない構成とし、架空の人気ランキングや再生数は表示しません。

**作品ページ**：作品名、紹介、作品画像、曲一覧、曲順、クレジット、OST再生ボタン。初期版は作品内の曲順を再生キューの基本にします。外部のゲーム紹介URLは任意ですが、GameLauncher連携は実装しません。

**曲詳細／再生画面**：曲に紐づく代表画像、曲名、作品名、作曲・編曲などのクレジット、任意の制作コメント、再生操作、区間ループ切り替え、共有用のURL。

**ミニプレーヤー**：他のページを閲覧しても、現在再生している曲の情報と再生・一時停止操作を表示。押すと再生画面へ戻れます。

作品と曲には直接開けるURLを付けてください。URLを開いただけで勝手に音を出さず、再生操作を待ちます。履歴の戻る・進むでも破綻しないようにしてください。

### 6.2 画像

1曲につき代表画像1枚を登録できます。作品のジャケット画像とは別のデータです。
元の縦横比を維持し、プレイ画面を無理に正方形へ切り抜かないでください。縦長画像にも対応し、画像がない場合は作品画像、さらに共通プレースホルダーへフォールバックします。

画像は再生位置に合わせて切り替えず、再生中の曲に紐づいた1枚を表示します。別作品を閲覧しても、プレーヤー内の画像は再生中の曲のものを維持します。
画像には代替テキストを持たせ、不要な原寸画像の一括取得を避けてください。

### 6.3 スマホ設計

360px、390px、430px程度の縦画面を中心に確認し、PC幅にも対応してください。主要操作は44px程度以上を設計目標とし、タッチ、キーボード、フォーカス表示、スクリーンリーダーのラベルにも配慮します。
画面下部のセーフエリアを確保し、ミニプレーヤーが曲一覧や保存ボタンを隠さないようにしてください。
長い日本語の曲名、英語のクレジット、画像なし、曲なし、通信失敗も扱います。

スタイルは落ち着いた音楽プレーヤー風とし、静止画と再生操作を主役にしてください。テーマ切り替えや凝ったアニメーションは完成を遅らせない範囲にとどめます。

### 6.4 プレーヤーの基本ルール

音声エンジンはルート遷移で破棄されない場所に1つ保持し、ページごとに新しい再生インスタンスを作らないでください。表示状態と実際の音声状態を同期させます。

再生モードは `off / track / queue / region` などの排他的な状態で表し、通常リピートと区間ループが同時に異なる指示を出さないようにします。シャッフルは独立した状態として構いません。
通常再生では曲末で次曲へ進み、最後の曲では停止します。全曲リピートでは最後から先頭へ戻ります。シャッフルは現在曲を突然切り替えず、キューが1曲・空のときも壊れないようにしてください。

再生前、読み込み中、再生中、一時停止、中断、エラーを区別し、読み込み失敗を「再生中」のまま表示しないでください。
曲の連打・シーク・前後移動による古い非同期処理は中止または無効化し、別曲が遅れて鳴る問題や二重再生を防ぎます。

## 7. 区間ループ【初期版の重要機能】

### 7.1 聴取時の仕様

例：音源長100秒、イントロ0〜12秒、ループ区間12〜90秒、アウトロ90〜100秒。

| 操作・状態 | 動作 |
|---|---|
| 通常再生 | 0秒から100秒まで再生し、次曲へ進む |
| 区間ループを有効にして先頭から再生 | 0〜90秒を流し、その後12〜90秒を繰り返す |
| イントロ中にループを有効化 | 現在位置を保ち、90秒到達後に12秒へ戻る |
| 区間内でループを有効化 | 現在位置を保ち、終了地点で開始地点へ戻る |
| 終了地点以後でループを有効化 | ループ開始位置から再生する |
| 区間ループを解除 | 現在の音源内位置を保ち、曲末まで流して次曲へ進む。通常リピートOFFに戻す |
| 一時停止・再開 | 現在の音源内位置とループ設定を維持 |
| 手動で次曲・前曲へ移動 | 区間ループ中でも移動可能。曲固有の区間ループは解除 |
| ループONで終了位置以後へシーク | ループ開始位置へ移動。UI上でもこの動作が分かるようにする |
| 非対応曲 | ボタンを無効化または非表示にし、通常再生は利用可能 |

最初の再生でループ開始位置を飛ばしてイントロを省略したり、ループごとにイントロへ戻したりしないでください。
初期状態は通常再生とし、対応曲でリスナーが「ゲーム内ループ」を選ぶ仕様にします。

### 7.2 投稿者による設定

管理画面で、曲ごとに有効・無効、開始位置、終了位置を編集します。
数値入力に加え、「現在位置を開始にする」「現在位置を終了にする」「つなぎ目を試聴」を用意してください。試聴は終了地点の少し前から再生し、開始地点へ戻る接続部分を確認できるものにします。波形エディターの実装は必須ではありません。

ループ地点は音源ファイルを切り詰めず、追加のメタデータとして保存します。精度を不必要に丸めず、音源のリビジョンと紐づけてください。
サンプル位置で保存する場合は基準サンプルレートを含めます。秒で保存する場合も小数精度を保ち、再生時に実際のデコード結果に合わせて境界を解釈してください。

`0 <= start < end <= duration`、有限数値、最低区間長をフロント・APIの両方で検証します。音源を差し替えた場合、旧音源のループ設定を無条件に引き継がず、再検証・試聴を促します。
管理画面の試聴とリスナー用再生が同時に鳴らないようにし、試聴開始時は通常のプレーヤーを一時停止させてください。

### 7.3 実装方式

**`timeupdate`、`setInterval`、`requestAnimationFrame`だけで終了地点を監視して `audio.currentTime` を戻す実装を、完成形にしないでください。**
区間ループは、Web Audio APIの `AudioBufferSourceNode.loop / loopStart / loopEnd`、または同等の精密な再生方式を採用してください。[R2][R3]

通常再生は `HTMLAudioElement` を用いる案を標準とし、精密な区間ループを有効にするときだけ、必要な音源をデコードする方式を検討してください。小規模なテスト用音源に限り共通のWeb Audioエンジンで実装する場合も、メモリ予算とフォールバックは省略しません。

音声エンジンを切り替える際は、現在位置を正しく引き継ぎ、旧エンジンを停止して二重再生を防ぎます。デコード中に曲が変わった場合は古い結果を反映しません。
`AudioBufferSourceNode`は再利用して再スタートできないため、一時停止後の再開やシークでは必要に応じて新しいNodeを生成します。バッファとNodeの寿命は区別してください。[R2]

位置の算出は音声クロックを基準に行い、画面の更新タイマーは表示専用にしてください。ループ解除時、一時停止・再開時、AudioContext中断時に積算時刻と実際の音源内位置がずれないようテストします。

元音源の波形やループ地点が不連続なら、再生エンジンだけではクリックノイズを除けません。音源由来の問題と実装由来の無音・途切れを分けて確認し、試聴で修正できるようにします。音楽を変えてしまう自動クロスフェードや末尾削除を勝手に適用しないでください。

### 7.4 メモリとスマホ

AudioBufferはメモリ上に展開された32-bit PCMを持ち、圧縮ファイルの容量と使用メモリは同じではありません。[R4]
概算のPCMサイズは `durationSeconds × sampleRateHz × channelCount × 4 bytes` です。48kHz・ステレオ・3分でPCMだけで約69.1MB（約65.9MiB）となり、実際には別の作業領域も必要です。

全曲の事前デコード・全曲の先読み・無制限のバッファキャッシュは禁止です。基本は必要な曲だけをデコードし、前曲の参照、Node、イベントリスナー、Object URLを適切に解放します。デコードの並列数と保持バッファ量を制限してください。
不適切なファイルや不明なメタデータを、サイズ確認もせず無制限にデコードしないでください。

デコード失敗、予算超過、非対応形式は理由付きで通知し、通常再生への復帰を可能にします。ただし、対応条件内のサンプル音源で区間ループが動かない状態を「通常再生に戻れるので完成」と扱わないでください。

ブラウザーの自動再生制限に合わせ、AudioContextの作成・再開や再生開始はユーザー操作を起点にします。[R5]
Media Session API等は対応している場合にメタデータや操作を連携しますが、バックグラウンド・画面ロック中の継続はブラウザーとOSの実測結果を記録し、未検証の保証をしないでください。中断時は画面表示を合わせ、復帰時にユーザーが再開できるようにします。

## 8. 投稿者の認証と権限

### 8.1 ロール

初期版の標準案は次の3区分です。

| 利用者 | できること |
|---|---|
| 未ログインのリスナー | 公開済み作品・曲の閲覧と再生 |
| 作品の担当者 | 割り当てられた作品の曲・画像・情報・ループ設定を登録・編集・公開・非公開化 |
| サイト運営 | 作品の作成、担当者の追加・解除、全作品の管理、緊急の公開停止、広告設定 |

作品の新規作成と担当者割り当ては運営が行う案にします。各担当者は、割り当てられた作品内であれば、自分以外の担当者がアップロードした曲も共同編集できます。
**作品内の曲の公開には、運営承認を要求しません。**

アップロードしたアカウントと作曲者クレジットは別です。作曲者全員にログインアカウントを作らせず、公開名と役割で正しく記録できるようにしてください。

### 8.2 認証方式の標準案

新規実装ではGitHub OAuthを第一案にします。ただし、GitHubでログインできることと、投稿権限を持つことは別です。
認証後の安定したGitHubユーザーIDとサイト内アカウントを紐づけ、サイト内の作品所属を毎回確認します。GitHubの表示名・ユーザー名だけで権限を判定しないでください。
任意のGitHubユーザーに投稿権限を自動付与しません。特定リポジトリのCollaboratorであることも、本プロジェクトの既定条件にはしません。

初期管理者の登録は、サーバー側のID許可リストまたは安全なbootstrap手順で行います。「最初にログインした誰かが管理者になる」実装は禁止です。

OAuthは `state` とPKCEのS256、Callback URLの固定、短命な認証途中状態を用い、プロバイダの公式手順に従ってください。[R6]
認証に必要な最小スコープだけを要求し、リポジトリ読み書き権限は要求しません。トークンをクライアントのlocalStorageやログに保存しないでください。

セッションは期限付きの安全なCookieを用い、本番ではHttpOnly・Secure・適切なSameSite設定を使用します。ログアウト、セッション失効、CSRF対策、Origin検証を実装してください。
担当者の解除や管理者ロール変更は、古いセッションが残っていても次のAPI操作で反映されるようにします。クライアントが送るロール・ユーザーIDを信用しません。

外部認証の設定がないローカル環境ではテスト用認証を利用できますが、本番buildまたは本番実行時に有効化できないガードを設け、テストしてください。テスト用ログインを本番に残さないでください。

## 9. 永続化・公開状態・共同編集

### 9.1 保存する情報

最低限、以下を扱えるモデル・スキーマを設計してください。

- 作品：ID、公開名、紹介、作品画像、公開状態、作成・更新情報。
- 曲：ID、所属作品、曲順、編集中リビジョン、公開中リビジョン、公開状態。
- 曲リビジョン：曲名、クレジット、コメント、音源Asset、曲画像Asset、ループ設定、編集者、更新日時。
- Asset：用途、所属作品、一意キー、形式、容量、検証状態、音源長等の検証済みメタデータ。
- アカウント・作品所属・セッション。
- 広告設定・バナー情報。
- 監査ログ：誰が、どの作品・曲に、何を行ったか。

クレジットは複数人と役割を扱い、公開名を保存します。内部アカウントID、メール、GitHub認証情報を公開APIに混ぜないでください。
必要な外部キー、ユニーク制約、インデックス、状態遷移の検証を設けます。音源と画像のバイナリをDBに格納しません。

### 9.2 下書きと公開版

音源をアップロードしただけで一般公開しないでください。初回は下書きに保存し、担当者が「公開する」を押したときに公開します。
公開済みの曲を編集するときも、一般公開版を直接書き換えず、編集中の変更を保存します。「更新を反映する」でまとめて切り替え、それまでは旧公開版を維持してください。

実装は「作業中データ＋公開スナップショット」程度で構いません。複雑な差分管理や履歴復元UIは不要です。
公開操作は、必要な入力・権限・音源と画像の検証・権利確認を満たしたときに、DB上で原子的に行います。公開中の音源URLだけ先に変更され、ループ設定が旧版のままになる状態を防いでください。

非公開化では一般向けの一覧、詳細、API、音源・画像への新しいアクセスを止めます。既に利用者へ送信・保存されたデータまで回収できるとは説明しません。
作品全体の非公開化・運営による停止も、その作品の公開入口を止める条件に含めてください。

### 9.3 競合・削除

共同編集はリビジョン番号などで楽観ロックし、古い内容の上書きは409等の競合として通知してください。黙って後勝ちで消さないでください。
初期の通常操作は下書き保存・公開・更新・非公開化を中心にし、物理削除は慎重に扱います。
R2とDBを1つのトランザクションだと仮定しないでください。アップロード失敗、DB保存失敗、公開失敗のそれぞれで、再試行と孤立Assetの回収ができるようにします。公開版が参照している音源を、下書き編集の都合で削除しないでください。

## 10. 音源・画像のアップロードと配信

### 10.1 投稿時

初期の標準対応形式は音源MP3 / PCM WAV、画像JPEG / PNG / WebPとします。実際に動作確認した形式・エンコード条件を投稿画面とREADMEに表示してください。
初期版では動画、SVG、HTML、実行ファイルを投稿対象にしません。自動トランスコードを完成条件に含めず、対応しない形式は明確に拒否します。

拡張子や申告MIMEだけを信用せず、実データの形式、容量、画像寸法、必要な音源メタデータを検証します。ファイル名をそのまま保存キーに使わず、サーバー生成の一意キーを使ってください。本文・コメント・外部URLも検証し、任意HTMLやスクリプトを通しません。[R7]

作品への編集権限を確認してからアップロードを受け付け、音源・画像は検証が完了するまで公開に使用しません。別作品のAsset IDを差し込んで流用・改ざんできないようにしてください。

新規の標準案は「認可済みAPIでストリーム受信 → 非公開R2の一意キーへ保存 → 検証 → DBに確定」です。Workersで巨大な `arrayBuffer()` や `formData()` による全件メモリ展開を避け、実行環境の上限を踏まえて設計します。[R8]

署名付き直接アップロードを採用する場合は、短い有効期限、操作・キー・Content-Typeの限定、必要なCORS設定、アップロード確定API、実容量・内容の再検証を設けてください。[R11]
署名URLが再利用されて検証後の内容が上書きされる問題を避け、検証対象と公開対象を同じ内容として固定します。CORSだけを認可対策にしないでください。

アップロードの進捗・失敗・再試行を表示し、複数ファイルは少数の同時処理に制限します。最初から無制限の並列アップロードや巨大ファイルの一括デコードをしないでください。

### 10.2 配信時

R2の公開URLを下書きにも付けて、UIから隠すだけの実装は禁止です。既定は非公開バケットとし、APIで公開状態またはプレビュー権限を確認してから返してください。

音源は全体取得と通常再生のRangeリクエストを正しく扱います。`HEAD`、`200 / 206 / 416`、Content-Type、Content-Length、Content-Range等を対象ブラウザーで確認してください。R2のWorkers APIが提供するrange等の機能を適切に使用します。[R12]

音源だけでなく、曲画像・作品画像の直URLや古いAsset IDも非公開データの露出経路として確認してください。公開済みの別コンテンツから参照されている共有Assetは、その参照関係を考慮します。
初期版は取り下げの分かりやすさを優先し、保護対象や状態が変わる配信レスポンスを無条件に長期パブリックキャッシュしないでください。

キャッシュを使用する場合も、公開状態・認可の確認より先にキャッシュ本文を返してはいけません。更新・非公開化・削除時の無効化方式を設計・テストしてください。認証付きプレビューは共有キャッシュに入れません。
音源へのアクセスを完全にコピー不能にするDRMは対象外であり、「ダウンロードボタンがないから保存できない」と説明しないでください。

### 10.3 権利確認と運営情報

投稿者が「音源・画像・クレジットの公開と、広告掲載のあるサイトでの利用について必要な確認を行った」ことを確認できる入力を用意します。運営承認待ちにはしません。利用許諾そのものをシステムが保証すると説明しないでください。

サイトについて、利用上の注意、プライバシーに関する説明、権利・削除依頼の連絡先を用意します。実在しない運営者名、住所、メール、法的な断定を作らず、未設定の必須事項は本番公開前のチェック項目として明示します。

## 11. 広告の初期実装

広告は運営費確保のために設置できるようにしますが、音楽再生を妨げない設計にしてください。

初期版の実装対象は、共通 `AdSlot` と、運営が管理できる「画像・リンク・代替テキスト」のバナー広告です。これで外部広告サービスの審査やアカウント設定がなくても、広告掲載機能を実装・検証できます。
外部広告プロバイダとの連携は、必要な箇所を分離するだけにとどめてよく、AdSense等のSDKの実接続は完成条件に含めません。未接続のものを接続済みと表示しないでください。

配置はホームのコンテンツ区切りや作品紹介の下などとし、広告であることを明示します。再生ボタンの隣、ゲーム画像への重なり、画面全体の強制表示、音声広告、再生前広告は禁止です。

運営は有効・無効を変更でき、初期設定は無効にしてください。無効時は空白の大きな枠を残しません。広告取得・表示の失敗や広告ブロッカーで再生機能が止まらないようにします。
設定を操作できるのは運営だけです。投稿者に広告コード入力欄を与えず、運営用にも任意JavaScriptや任意HTMLを保存して実行する仕組みは作りません。

初期バナーでは不要な追跡を入れません。将来、第三者広告サービスを有効にする場合の審査、ポリシー、プライバシー表示、同意要件の確認を運用文書へ記録してください。法律や広告サービスの条件を実装側で勝手に満たしたことにしないでください。

## 12. 投稿者・運営の管理画面

最低限、担当作品一覧、作品情報編集、曲一覧・曲順変更、曲登録・編集、音源・画像アップロード、ループ設定・試聴、プレビュー、公開・更新反映・非公開化を実装してください。
管理画面もレスポンシブにし、スマホで最低限の登録・公開操作ができるようにします。ループ地点の微調整などはPCでも扱いやすい設計にしてください。

複数曲の一括アップロードは、複数の下書きをまとめて作成する範囲で対応します。音源名を初期の曲名候補として利用してもよいですが、自動公開しません。曲順はドラッグだけに依存せず、上下移動や数値でも変更できるようにします。

作品内の準備済み曲をまとめて公開する操作を用意する場合は、対象曲一覧と検証結果を示し、選択した対象を原子的に公開するか、失敗状態が曖昧にならない方式にしてください。複雑な予約公開は不要です。

運営画面には、作品作成、担当者の割り当て・解除、広告設定、公開停止、簡易な更新履歴を用意します。収支・決済管理は不要です。

入力中のエラーは該当項目に表示し、保存成功・失敗を明確に伝えます。未保存の変更を破棄する操作には注意を出し、二重送信を防いでください。完成していない機能のボタンを押せる状態で残さないでください。

## 13. エラー処理とセキュリティの共通条件

一般向けAPIと管理APIを分離し、公開APIのDTOに下書き、内部キー、アカウント情報を混ぜないでください。
公開状態と作品単位の認可は、一覧取得、詳細、更新、公開、非公開化、曲順変更、アップロード開始・確定、Asset読取のすべてで確認します。

400系の入力エラー、401、403、404、409、容量制限、429、500系を区別し、UIが復旧方法を表示できるエラーコードを用意します。内部エラーやSQL、トークンをそのまま返さないでください。

パラメーター化SQL、入力検証、出力エスケープ、CSRF対策、適切なセキュリティヘッダー、アップロード・認証操作の回数制限を実装してください。ブラウザーでボタンを隠すだけの認可は禁止です。
監査ログと障害ログに必要な操作情報を残し、秘密・Cookie・OAuthコード・署名URLを記録しないでください。監査ログへの一般投稿者からの任意追記・削除は認めません。

## 14. テストと受け入れ条件

### 14.1 自動テスト

純粋なドメインテストはDB・ネットワーク・ブラウザーなしで実行できるようにします。
ループ値の境界、状態遷移、実際の再生位置の計算、キュー、通常リピート、シャッフル、作品権限、公開条件、入力・設定値検証をテストしてください。

音声の評価をUIテストだけで済ませないでください。可能な範囲で同じAudioEngineのスケジューリング処理をOfflineAudioContext等で検証し、連続する検証用波形でイントロが1回だけ再生されること、区間が意図した位置で繰り返されることを確認します。
モックの音声エンジンだけが成功していても、実際の区間ループの完成証拠にはなりません。

DB/API統合テストでは、別作品IDによる変更、別作品のAsset差し込み、未認証操作、解除済み権限、公開スナップショット、競合、未検証Assetの公開、非公開Assetの直接取得、アップロード失敗と再試行を確認してください。

### 14.2 ブラウザーと実機

PCの主要ブラウザーに加え、iOS SafariとAndroid Chromeを確認対象にします。Playwright等のWebKitやスマホ画面エミュレーションを、iPhone実機での音声・バックグラウンド動作の検証と同一視しないでください。
実機が利用できない場合は、自動検証した範囲と実機未検証の項目を分け、実機用の手動チェックリストを残します。未実施を合格にしてはいけません。

| 確認項目 | 合格条件 |
|---|---|
| 公開聴取 | 未ログインで2作品分のテスト曲を閲覧・再生できる |
| 画像連動 | 曲を切り替えると、その曲の代表画像へ切り替わる |
| ページ移動 | 再生位置・音・再生キューを維持して画面移動できる |
| 基本操作 | 一時停止・再開・シーク・前後移動・曲末遷移が正しい |
| 通常リピート | 1曲・キューの動作がそれぞれ正しい |
| 区間ループ | イントロ1回、設定区間を少なくとも10回繰り返してもドリフトや実装由来の隙間が発生しない |
| ループ解除 | 現在位置から曲末まで自然に進み、次曲へ移動する |
| 再生競合 | 連打、曲変更中のデコード完了、試聴開始でも二重再生しない |
| メモリ | 全曲を同時デコードせず、繰り返しの曲変更で保持メモリが無制限に増えない |
| 中断復帰 | 通信失敗・AudioContext中断時に状態表示が一致し、再試行できる |
| 管理 | 担当者が登録・編集・公開・非公開化を自分で完結できる |
| 事前承認なし | 有効な担当者の公開操作に運営承認が要求されない |
| 認可 | 他作品の曲・画像・ループ・曲順をAPI直接操作でも変更できない |
| 公開版の維持 | 下書き編集の途中では公開中の内容が変わらない |
| 非公開保護 | 非公開化後の新規公開API・Assetアクセスが止まる |
| 広告 | 運営だけが変更でき、OFF・取得失敗・ブロックでも再生できる |
| スマホUI | 主要幅で横スクロールや操作部の重なりがなく、画像全体を見られる |
| セキュリティ | 本番で開発用認証を有効化できず、クライアントに秘密が含まれない |
| 保守性 | Domainの外部依存禁止、型チェック、lint、テスト、buildが通る |
| コメント | 自作関数のドキュメントコメントと意味のあるブロックコメントがある |

`docs/test-report.md` に、実行コマンド、日時、ブラウザー／端末、結果、未検証事項を記録してください。コンソールにエラーがないことだけで、聴感上の継ぎ目を合格にしないでください。

## 15. 実装の進め方

1. **既存調査と骨格**：ワークスペースを確認し、採用構成と依存方向を短く記録。ローカル起動、型チェック、lint、テスト基盤を用意。
2. **再生の小さな検証**：権利上問題のないテスト音源で、スマホ向けプレーヤーと区間ループを先に検証。音源メモリ量と中断の課題を記録。
3. **Domain / Application / DB**：作品、曲、Asset、リビジョン、所属権限、ループ、公開Use Case、マイグレーションを実装。
4. **認証・投稿・公開**：安全な認証境界、担当作品の管理、アップロード、プレビュー、公開・非公開化を接続。
5. **一般向け画面と永続再生**：ホーム、作品、曲、画像、ミニプレーヤー、キュー、区間ループを実データへ接続。
6. **広告・仕上げ・検証**：運営バナー、エラー処理、アクセシビリティ、セキュリティ、E2E、運用手順を仕上げる。

検証用のモックは途中段階に限り、最終的な投稿・公開・配信をモックだけで完成扱いにしないでください。作業が長くなる場合も、未完了項目を記録しながら実装を進めてください。

## 17. 禁止事項と最終報告

以下は行わないでください。

- 区間ループを将来対応へ戻す、またはタイマーでの位置戻しだけを完成扱いにする。
- 投稿者の公開に運営承認を追加する。
- リスナーへログインや課金を必須にする。
- 投げ銭・動画・GameLauncher連携を先回りして実装する。
- 2作品・10曲を登録上限としてハードコードする。
- UIやAPIの各所に調整値・業務ルールを重複させる。
- フォルダを分けるだけで、DomainがDBやブラウザーAPIへ依存する。
- コメント規則を「コードが自明だから不要」として省略する。
- 非公開素材を誰でも取得できる公開URLへ置く。
- 各ページで音声エンジンを作成する、全曲をデコードする、二重再生を放置する。
- 本番にデモ認証、架空データ、秘密値、未設定の実広告コードを混入させる。
- 確認していない本番接続、実機動作、広告審査、バックグラウンド再生を成功と報告する。

最終報告には、実装した機能、主要な設計、採用した標準案と変更点、実行したテストと結果、起動方法、ユーザーが設定する必要のある値、本番公開前の残事項、未検証のブラウザー動作を含めてください。
完了・未完了・外部設定待ちを区別し、実行していないコマンドを成功と報告しないでください。

**完成の中心は「担当者が自分で登録・公開し、学外の人がスマホで曲ごとのゲーム画像を眺めながら通常再生と区間ループを楽しめる」ことです。**
