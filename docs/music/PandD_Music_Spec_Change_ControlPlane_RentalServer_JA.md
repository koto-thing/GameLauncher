## 0. Codexへの依頼と指示の優先順位

PandD Musicの初期版について、元指示書の技術構成を本書に従って変更し、実装してください。

**音楽管理システムを別に新設するのではなく、GameLauncherの既存control-planeにMusic管理機能を追加してください。一般公開サイト・楽曲・画像・公開情報はレンタルサーバーから配信し、通常の閲覧・再生ではWorkersを一切呼び出さない構成にします。**

優先順位は「今回のユーザーの明示的な指示 → 本書 → 本書と矛盾しない元指示書」です。リポジトリの `AGENTS.md` / `agents.md` 等も確認し、指示の衝突があれば理由と対応を報告してください。

元指示書の製品要件、クリーンアーキテクチャ、調整値の集約、コメント規則、スマートフォン対応、区間ループ、セキュリティ要件は継続します。保存先の変更を理由に、非公開素材の保護や音声の検証を削らないでください。

元指示書は読みやすい位置に保存し、本書とセットで参照してください。既に元指示書の実装が進んでいる場合、再生UI・ドメイン・テストなど再利用できる成果を残し、外部接続と管理画面の配置を段階的に変更してください。作り直しや既存データ削除を先に実行しないでください。

## 1. 今回の必須条件

1. 一般の人のページ表示、作品・曲情報取得、画像表示、音楽再生、シーク、区間ループは、レンタルサーバーと利用者の端末だけで完結する。
2. 既存control-planeのGitHubログイン、管理画面の共通部分、D1接続などを活用する。
3. 管理者・作品担当者がcontrol-planeからMusicを登録・編集・公開・非公開化できる。
4. Musicの公開に運営承認を追加しない。既存ゲームの公開承認は弱めない。
5. Music専用の担当者に、GameLauncherリポジトリの書き込み権限やゲーム公開権限を要求・自動付与しない。
6. Music機能が未設定・無効・障害中でも、既存のゲーム管理が動作する。既存データを壊さない。
7. control-planeが停止していても、レンタルサーバーで既に公開済みのMusicサイトを利用できる。
8. 下書き・古い非公開版・音源原本・バックアップを、推測困難なURLだけに頼って保護しない。
9. 本番公開、DNS変更、有料契約、既存リソース削除、既存GitHub Appの権限拡張を無断で実行しない。
10. 設計書だけで終わらず、ローカルで登録から公開・聴取まで動く実装とテストを作る。認証情報や実機がない部分は未検証として報告する。

## 2. 維持する初期版の製品仕様

| 項目 | 維持する仕様 |
|---|---|
| 規模 | 初回は2作品・合計5〜10曲。件数のハードコード上限ではない |
| 聴取 | 一般公開、無料、ログイン不要、スマートフォン優先 |
| 表示 | 1曲につき代表静止画1枚。縦横比を維持。作品画像へのフォールバック |
| 基本再生 | 再生・一時停止・シーク・前後移動・連続再生・通常リピート・シャッフル |
| 永続再生 | 公開サイト内のページ移動で再生エンジンを破棄しない |
| 区間ループ | イントロを1回流し、投稿者が指定した1区間を精密に繰り返す。元指示書第7章を維持 |
| 投稿 | 作品単位の共同編集、複数曲の下書き作成、曲順・クレジット・コメント編集 |
| 公開 | 下書きと公開版を分け、担当者自身が公開・更新・非公開化する |
| 広告 | 運営専用の画像・リンク・代替テキストによるバナー。初期OFF。再生を妨げない |
| 将来対応 | 投げ銭、動画、ランチャー本体からのリンク。今回は画面・SDK・テーブルまで先回りして作らない |

初期版の音源はMP3 / PCM WAV、画像はJPEG / PNG / WebPを標準とし、実際に検証した条件を表示します。自動音源変換、任意HTMLのページ編集、任意JavaScriptの広告登録、波形編集の大規模実装は追加しません。

将来の投げ銭はサイト全体の運営費に充て、作曲者・作品別に分配しない方針を文書に残すだけにしてください。

## 4. 新しい全体構成

```text
担当者のブラウザー
  └─ 既存control-planeのMusic管理画面（Workers）
       ├─ 共通GitHub Appログイン・セッション
       ├─ Musicの作品別認可
       ├─ Music用Domain / Application
       ├─ D1：担当者、下書き、素材情報、公開処理、監査
       └─ HTTPSの署名付き管理要求
             └─ レンタルサーバーのMusic専用PHP API
                  ├─ 素材の受信・検証・私有保存
                  └─ 公開版の切り替え・取り下げ

一般リスナーのブラウザー
  └─ レンタルサーバーの公開Musicサイト
       ├─ HTML / CSS / JavaScript
       ├─ ローカル公開版から得た作品・曲・広告情報
       ├─ ローカルの公開判定を経た画像・音源
       └─ ブラウザー内の音楽再生・区間ループ

一般リスナーからWorkers / D1 / GitHubへの必須通信：なし
```

PHPをレンタルサーバー内の読み出し・公開状態確認に利用することは許可します。「Workersを通さない」は「PHPを一切使わない」という意味ではありません。公開サイトにNode.js常駐サーバー、Next.jsのSSRサーバー、Workersの画像最適化等を要求しないでください。

管理プレビューは管理操作なので、認可済みcontrol-plane経由で音源・画像を取得して構いません。公開再生とプレビューのコード経路・権限を明確に分離してください。

## 5. コード配置とクリーンアーキテクチャ

次は配置案です。既存ワークスペースに適した名称を選べますが、責務は混ぜないでください。

```text
apps/admin-web/
  app/music/                    # 新しいMusic管理画面
  app/api/music/                # 新しいMusic管理API
  music/
    domain/                    # 曲・作品・権限・ループ・公開ルール
    application/               # Use Case / Port / DTO
    infrastructure/            # D1・共通認証Adapter・PHP API Client
    presentation/              # 管理用の表示・入力変換
    composition/               # 依存の組み立て
    config/                    # 調整値の初期値

apps/music-web/                # レンタルサーバーへ配置する静的アプリ
  src/                         # 公開UI・プレーヤー・公開データAdapter

server/music/
  public/                      # catalog / media / bridge等の限定入口
  src/                         # PHPの検証・保存・公開切替・読出し
  config/                      # 秘密値を含めない設定テンプレート
  tests/

contracts/music/               # 公開DTO・管理プロトコル等の版付き契約
```

公開プレーヤーと管理試聴で共有する純粋ロジックがある場合、既存のworkspace方針に合わせて小さな共有パッケージ等へ切り出します。共有のためだけにリポジトリ全体をmonorepoへ再編しないでください。

依存方向は `Presentation → Application → Domain`、`Infrastructure → ApplicationのPort` を基本とします。DomainからReact、Cloudflare、D1、HTTP、PHPファイルシステム、Web Audio APIを参照しません。

`RentalServerPublisher`、`MusicAssetStorage`、`MusicRepository`、`MusicAuthorization`、`AudioEngine` など、必要な境界だけをPort化してください。既存 `control-plane.ts` / `ControlPlane.tsx` へ音楽用の大量の分岐・SQL・配信処理を詰め込まないでください。

PHP側もルーター1ファイルに署名検証・ファイル操作・公開判定を混在させず、役割ごとに関数・クラスへ分けます。大規模フレームワークや独自DIフレームワークは不要です。

## 6. 認証・認可の統合【最重要】

### 6.1 本人確認とサービス別認可

GitHub Appの本人確認・Cookieセッションは共通化します。一方で「誰か」と「どの機能・作品を扱えるか」は別々に検証します。

| 利用者 | ゲーム管理 | Music管理 |
|---|---|---|
| 未ログイン | 不可 | 不可。公開サイトの聴取だけ可能 |
| GitHub認証のみ・登録なし | 不可 | 不可。権限なしを表示し、自動登録・公開権限付与はしない |
| Music作品担当者のみ | 不可 | 担当作品の登録・編集・公開・非公開化 |
| ゲーム担当者のみ | 既存権限の範囲 | Music担当の明示的な割り当てがなければ不可 |
| Music運営 | ゲーム権限とは独立 | Music作品作成、担当割当、全作品管理、広告、公開停止 |
| 両方の権限を持つ人 | それぞれの条件を満たす範囲 | それぞれの条件を満たす範囲 |

Music担当者には、GameLauncherリポジトリのCollaborator資格を必須にしません。安定したGitHubユーザーIDを用いて、Music運営が対象作品へ割り当てます。表示名・ログイン名だけで認可しないでください。

初期Music運営は既知の管理者IDを安全な手順で明示登録します。ログイン順で管理者を決めたり、全CollaboratorへMusic運営を付与したりしないでください。既存ゲームのAdminとMusic運営を同一人物にすることは可能ですが、意図的な割り当てとして扱います。

### 6.2 既存ゲームの権限を弱めない移行

現在の `verifyGithubToken()` を単に「GitHubの `/user` が成功したら許可」に変更するだけの対応は禁止です。[C2]

本人確認を共通部へ切り出し、ゲーム管理では従来のリポジトリ条件と申請・承認等の権限を引き続き適用してください。旧関数をゲーム向けの厳しい互換Wrapperとして残す方法も可能です。

ブラウザーAPIだけでなく、既存のBearer/Device Flow uploader、管理API、ダッシュボード読取、Server Action、権限変更、Actions起動、機械用OIDC入口まで洗い出してください。Musicの追加を理由に、機械認証や既存のGitHub Appインストールトークン条件を変更しません。

Music本人確認時にGameLauncherのリポジトリ参照ができなくても、それだけでMusicログインを失敗させない設計にします。ただし、同じ状況でゲーム管理を許可してはいけません。GitHubの認証失敗と、ゲーム用リポジトリへの認可不足を区別します。

既存セッションにない新しい権限フラグを、暗黙に許可として補完しないでください。必要な場合は安全な再認証を要求します。セッション互換性のために権限チェックを省略しません。

### 6.3 管理画面のデータ境界

Music専用アカウントに既存のゲーム用 `getDashboard()` を呼ばせてから一部を隠す設計は禁止です。既存関数はゲームの申請・権限・利用者等を扱っています。[C3]

共通ナビゲーションには利用可能な機能の情報だけを渡し、ゲーム管理とMusic管理のデータ取得を分けます。Music専用アカウントでログインした場合、権限のないゲーム画面を経由せずMusic管理へ移動できるようにしてください。

全Music APIで現在の割り当てを確認します。作品・曲・画像・音源・ループ・公開操作IDの別作品差し込み、一般担当者からの広告・担当者変更を拒否します。割り当て解除・停止を次の管理操作から反映し、古いCookie内のフラグだけを信用しません。

### 6.4 認証の安全性

既存GitHub Appを利用し、不要なOAuth App、独立したパスワード認証、別SSO基盤を作りません。Callback、既存Device Flow、既存ゲーム側のGitHub App権限は互換性を確認します。

ブラウザーの認可コードフローは `state` とPKCE S256、Callback固定、適切なCookie保護を確認・実装してください。GitHub Appの認証フローと権限の扱いは公式資料で確認します。[R1][R2]

管理APIのCSRF/Origin検証、ログアウト・期限、開発用認証の本番防止、秘密値の非公開を維持します。公開Musicサイトへcontrol-planeのCookieを共有するために、Cookie Domainを親ドメイン全体へ広げないでください。CookieやユーザートークンをPHPへ転送しません。

## 7. D1の使い方とデータの責任範囲

既存のD1接続・migration基盤を利用し、Music用テーブルは `music_` 等の明確な名前で追加します。既存のゲーム用テーブル・制約・監査チェーンを変更する必要がある場合は、最小の追加変更と回帰テストを伴わせます。既存migrationを書き換えて本番の適用履歴を壊さないでください。

初期モデルの候補：Music運営権限、作品、作品担当者、曲、曲リビジョン、クレジット、Asset、公開処理、Music監査、広告設定。

- D1は、下書き・担当権限・素材情報・公開したい版・処理状況の管理元です。
- レンタルサーバーの現在の公開版は、実際にリスナーへ配信される状態です。
- D1の「公開済み」は、レンタルサーバーへ反映された版を確認して更新します。
- 音源・画像のバイナリはD1に保存しません。レンタルサーバー上のAsset ID、検証済みメタデータ、digest等を保持します。
- 実ファイルの形式・容量・digest等については、PHPの検証結果を確認してD1に反映します。ブラウザーの自己申告だけで検証済みにしません。

Music用の公開処理を既存 `deployment_requests` に偽のゲーム申請として登録しないでください。監査基盤を再利用する場合も、既存の `request_id` の意味・外部キー・署名対象・連番を壊さず、必要ならMusic監査を別テーブルにします。[C3]

Music作品IDはMusic内で成立させます。既存ゲームとの対応IDを任意で持つことは可能ですが、ランチャー登録済み・Staging成功済みであることをOST登録条件にしません。ユーザー名、OAuth情報、内部保存パス等を公開DTOへ混ぜないでください。

## 8. 素材アップロードと管理プレビュー

### 8.1 初期版の標準経路

```text
管理ブラウザー
  → control-planeのMusicアップロードAPI
  → 認証・作品単位の認可
  → 署名付きHTTPSでPHPへストリーム転送
  → 非公開の一時保存・内容検証
  → 一意のAsset IDで変更不能な素材として確定
  → D1に検証結果を登録
```

この経路は管理操作時だけなのでWorkers経由を許可します。Musicのために既存ゲームIntakeを改造したり、ゲーム用ZIPを作ったり、R2を経由したりする必要はありません。

Workersでは巨大な `arrayBuffer()` / `formData()`、全音源デコード、音源変換を行わず、raw bodyをストリームで転送します。Streams APIは大きな本文の全量バッファリング回避に使えますが、CPU・HTTP本文サイズ等の制限がなくなるわけではありません。[R3][R4]

投稿開始時にAsset ID・upload ID・作品ID・上限・予定形式等を固定します。PHPは実際の受信byte数、形式、画像寸法、音源長、必要なdigestを検証し、違反時に公開可能なAssetを作りません。Workerはブラウザー由来のCookie・認証ヘッダーを外部へ転送しません。

単一リクエストで転送できる上限を、契約環境・PHP設定・Workers側・アプリ側で確認してください。ロリポップではPHPの設定項目が提供されていますが、具体的な契約プラン・有効値は未確認です。[R5]

環境上必要な場合だけ、上限付きの分割アップロードへ拡張します。分割する場合はupload ID、part番号、partサイズ、総容量、所有作品、digest、確定操作を検証し、任意位置への追記や確定済み素材の上書きを禁止します。制限を避けるために業務上の上限を勝手に極小へ下げて完成扱いにしないでください。

### 8.2 失敗・再試行

受信途中、検証失敗、DB保存失敗で公開データを変更しません。再試行は同じupload IDと同じ内容について安全に実行でき、別内容でのID再利用は拒否します。確定済みAssetの内容は書き換えず、差し替えには新しいAsset IDを発行します。

孤立した一時素材を後で回収できるようにし、進捗・失敗理由・再試行を表示します。公開版・下書き・実行中操作・バックアップが参照する素材を誤って削除しないでください。

### 8.3 プレビュー

管理画面の未公開素材の試聴・画像確認は、同一originのMusicプレビューAPIを通します。APIは現在の作品権限を検証し、PHPへ用途限定の署名要求を送り、データをストリームで返します。

PHP側の一般向けmedia入口にはプレビューを許可しません。管理Cookieや長期共有SecretをブラウザーからPHPへ直接渡しません。プレビューを共有キャッシュへ保存せず、公開再生と管理試聴が同時に鳴らないようにします。

## 9. レンタルサーバーの管理APIと保管領域

### 9.1 管理APIの用途制限

PHPの管理APIは、素材受信・検証結果確認・管理プレビュー・公開版反映・取り下げ・操作状態確認に限定します。初期設置したプログラム自体の更新は、通常のコードデプロイ手順で行います。

任意パスへのファイル書き込み、任意URLからの取得、shell実行、PHP/HTML/SVG/実行ファイルのアップロード、`.htaccess` や既存ゲーム領域の上書きを可能にしません。自由なファイル操作APIや汎用の署名生成APIを作らないでください。

Workersの接続先は環境設定の固定HTTPS originと固定パスに限定し、リクエストのパラメータから任意の接続先へ変更しません。リダイレクトを無条件に追跡して署名・Secretを別ホストへ送らないでください。TLS検証を無効にしません。[R6]

### 9.2 WorkersとPHP間の署名

既存ゲームの署名鍵、GitHub App秘密鍵、SESSION_SECRETとは**別のMusic連携用Secret**を用います。十分な乱数で生成し、Workers SecretとPHPの非公開設定に保管します。Git、HTML、bundle、監査payload、エラーレスポンスに含めません。

初期標準はHTTPS＋HMAC-SHA-256の要求署名です。小さな署名エンベロープに、少なくとも次を結び付けます。

| 項目 | 用途 |
|---|---|
| protocolVersion / keyId | プロトコルの版と鍵ローテーション |
| audience / environment | 別サービス・検証/本番への転用防止 |
| method / 許可されたpath | 署名を別の操作へ転用させない |
| issuedAt / expiresAt / nonce | 期限・未来日時・リプレイの検証 |
| operationId / uploadId | 論理操作の同定、冪等な再試行 |
| actorId / gameId / assetId / 操作種別 | 操作の主体・対象・用途の固定 |
| expectedRevision / payloadDigest | 版の競合、本文のすり替え防止 |
| 予定byte数・形式・fileDigest | アップロードの内容拘束。PHPが実体と照合 |

署名する文字列のUTF-8、改行、JSONまたはbase64urlの形式、数値表現、queryの許可、大小文字を仕様化し、TypeScriptとPHPの共通テストベクターを用意してください。曖昧な文字列連結や同じ意味の別表現を放置しません。

大きなファイル全体をWorkerでメモリに読み込んでから署名する必要はありません。認可済み操作の小さなメタデータと予定digestを署名し、PHPが実際のファイルを読みながらサイズ・digestを検証します。digestが一致しても、安全な形式であることの検証は別途必要です。

PHPは署名・期限・対象を検証してから、nonceを原子的に使用済みにします。nonceを無限に保存せず、有効期限と整合した削除を行います。再試行は新しいnonceで同じoperation IDを使い、同じoperation IDで異なる本文・対象を受け付けません。署名比較には `hash_equals` 等の適切な比較を用います。[R7]

署名はWorkerからの要求を認証するものであり、作品認可の代わりではありません。Worker側で本人・作品・用途を検証した結果からエンベロープを生成し、PHP側も自分が保持する素材所属や対象範囲と照合します。Music担当者が他作品を指定した要求に署名してもらえる構造は禁止です。

### 9.3 保管領域

音源・画像の実体、下書き、公開履歴、操作receipt、一時ファイル、鍵、ログは、可能ならdocument rootの外へ配置します。外へ置けない契約環境では、サーバー設定でHTTP直接アクセスを拒否し、その拒否を本番相当のHTTPテストで確認してください。保護を成立させられない環境では本番公開を可能扱いにしません。[R8]

全素材はサーバー生成IDに基づき保存します。入力のファイル名・拡張子・pathを保存先にせず、path traversal、二重拡張子、シンボリックリンク、別作品のAsset IDの流用を検証します。

ファイルの実行権限は与えず、プログラムとデータの配置を分離します。PHPの実行ユーザーに必要な書き込み領域だけを用意し、APIとしてもMusicデータ外を変更できないようにします。同じ共有サーバーにある他サイトを、この仕組みで編集可能にしません。

## 10. 公開・更新・非公開化の整合性

### 10.1 前提

**D1とレンタルサーバーのファイルを、1つのDBトランザクションとして扱ってはいけません。**

下書きの保存だけでは公開版を変えません。投稿者が公開操作を行った時点の曲情報・Asset・ループ設定・画像・クレジットを固定し、公開対象のスナップショットとして扱います。反映待ちの間に下書きを編集しても、実行中のスナップショットを変更しません。

初期版は小規模なので、Musicサイト全体の公開切り替えを直列化する方式でも構いません。大規模なキュー基盤・分散トランザクションシステムを追加する必要はありません。

### 10.2 標準的な処理順

1. control-planeが現在の担当権限、入力、権利確認、素材検証、下書きリビジョンを確認する。
2. D1内のトランザクション等で、不変の公開要求・operation ID・payload digest・対象版を記録する。同じ作品で競合する処理を無言で上書きしない。
3. PHPへ署名要求を送る。PHPは対象範囲、素材の所属・存在・検証結果、期待する現在版を確認する。
4. PHPは現在の公開版に**今回許可された対象の変更だけ**を適用し、新しい公開スナップショットを私有領域に完全生成する。
5. 排他制御の下で現在版を再確認し、公開版への参照を1か所で切り替える。成功後に反映済みoperation ID・公開版・digestを返す。
6. control-planeは応答内容を確認し、D1に反映済み版を記録する。利用者へ「公開済み」と表示するのは実反映を確認した後にする。

別作品の下書きを混ぜた全件上書きを行わないでください。作品Aと作品Bが同時に公開された場合、競合を検出して最新の公開版へ対象変更を適用し直します。古い一覧JSONを後から送ったために他作品の更新が消える動作は禁止です。

### 10.3 レンタルサーバー内の切り替え方式

初期標準は「私有領域の変更不能な公開スナップショット ＋ 現在版を示す小さな参照ファイル」です。スナップショットには、公開DTO、公開許可Assetの対応、revision、operation ID、digest等を含めます。外部には公開DTOだけを返します。

新しい素材とスナップショットを準備してから、同一ファイルシステム上の一時ファイルを用いて参照を置換します。複数JSONへの逐次上書きや、公開中のJSONへの直接追記は行いません。`rename`・`flock` 等の動作は対象OS・ファイルシステム・PHP実行環境で検証し、原子的な置換やロックを無条件に保証しないでください。[R9][R10]

ロックは置換対象そのものではなく安定したロックファイル等を使い、すべての公開書き込み経路で同じ方式を守ります。読み出しは1回の要求で1つの公開版を使用します。音源を長時間送信している間、公開更新のグローバルロックを保持しません。

初回の正常な未公開状態と、公開版ファイルの破損・消失を区別してください。破損時に古い公開版を無条件で戻して、取り下げ済み曲を復活させる処理は禁止です。整合性不明時は安全側でエラーとし、明示した復旧手順へ進みます。

### 10.4 応答消失・再試行・取り下げの順序

公開処理の状態は、少なくとも「未送信/準備中」「反映要求中」「反映済み」「失敗」「結果不明」を区別します。名前は実装に合わせて構いません。

| 障害・競合 | 必須動作 |
|---|---|
| 送信前に失敗 | 以前の公開版を維持し、再試行できる |
| 参照切り替え前にPHPが失敗 | 不完全な版を公開せず、以前の版を維持 |
| PHPの切り替え後にHTTP応答が失われる | 結果不明としてoperation IDで照会。新しい別操作として無条件に再公開しない |
| PHP成功後にD1の更新が失敗 | レンタルサーバーの反映済み版を照合し、D1を追いつかせる。公開内容を勝手に戻さない |
| 同じoperation ID・同じ内容が再送される | 記録済み結果を返すか安全に継続。二重公開・二重登録しない |
| 同じoperation ID・異なる内容が送られる | 409等で拒否 |
| 古い版の公開操作が遅れて到着する | 期待revisionと順序を確認し、新しい公開・取り下げを巻き戻さない |
| 別作品の更新が先に完了した | 最新の公開版を基に、自分の対象変更だけを再適用 |

PHP側にもoperation receiptを永続化します。「参照切り替え直後・receipt確定直前」で停止しても、現在版・私有スナップショット・操作journalからコミット結果を判定できるようにします。コミット前に作ったスナップショットが存在するだけで、反映済みと判断してはいけません。

結果不明の操作を解決しないまま、競合する古い操作を後続に混ぜないでください。管理画面の状態照会・再試行で復旧できるようにし、常時稼働の短周期ポーリングや有料キューは初期版の必須にしません。

取り下げ要求がサーバーへ未反映なら、D1だけを変更して「非公開化完了」と表示しません。到達不能時は「取り下げ未反映」と明示します。サーバー管理者が使う緊急停止のローカル手順も文書化します。

### 10.5 人の承認と技術的な検証は区別する

署名検証・入力検証・ファイル検証・公開反映待ちは必要ですが、人の承認待ちは追加しません。音楽の公開で既存ゲーム用のGitHub Actions、Staging/Production承認、申請者とは別人の承認を呼び出さないでください。

サイトのプログラム自体を更新するときにCIでbuild/testすることと、担当者が曲・説明文を公開するときの処理は分けます。曲名やループ地点を変更するたびにサイト全体のbuildを要求しません。

## 11. 一般公開サイトと配信方式

### 11.1 静的アプリ＋ローカルの公開データ

公開アプリはReact＋Vite等でbuildした静的ファイルとしてレンタルサーバーへ配置します。既に適切な実装がある場合は再利用してください。

作品紹介・曲一覧・画像参照・音源参照・ループ地点・広告設定は、レンタルサーバー内の公開版から取得します。例として `/catalog.json` をPHPへrewriteし、現在版の公開DTOだけを返す方式が使えます。

これはサーバー内に確定済みのデータを読むだけの経路です。PHPからWorkers・D1・GitHubへ問い合わせてはいけません。画面の見た目・プレーヤーの変更はコードデプロイ、作品情報・曲の追加は公開データ更新と切り分けます。

公開側の広告も同じ公開版から読みます。広告の取得にcontrol-planeのAPIを使わず、担当者が編集できない運営設定として公開反映します。

### 11.2 直接URLからの非公開素材漏えいを防ぐ

初期標準では素材の実体を私有領域に保管し、`/media/{assetId}` 等をPHPへ振り分けます。PHPは現在のローカル公開版でそのAssetの利用可否を確認してから送信します。

この判定はレンタルサーバー内で完結させます。リスナー用の署名URLをWorkersで毎回発行する、公開許可のキャッシュが切れたらD1を参照する、といった設計は禁止です。

曲画像、作品画像、音源、HEAD、Range、古いAsset IDのすべてで公開確認を行います。複数の公開項目から正当に参照されるAssetは、その参照を考慮します。下書きや過去版だけの参照を理由に一般配信を許可しません。

非公開化が完了した後の新しいHTTP要求には、元のmedia URLでも内容を返しません。304や206の判定より先に公開確認を行います。既に許可され転送開始済みの要求、ブラウザーにダウンロード済みの音源、メモリ上のループまで回収・停止できるとは説明しません。

ネイティブのWebサーバー配信へ切り替える最適化は、同等の取り下げ・下書き保護を実証できる場合だけ許可します。初期版のために未確認のX-Sendfileやサーバーモジュールを必須にしません。

### 11.3 HTTP・キャッシュ・再生

`GET` / `HEAD`、全体取得、単一byte Range、suffix Range、範囲外、正しいContent-Type/Length/Rangeを検証します。`206`・`416`等の扱いはHTTP仕様に合わせ、サポートしない複数Rangeの扱いも明記します。[R11]

音源全体をPHPのメモリへ読み込まず、必要範囲をストリームで送ります。音源送信に不要なPHPセッションロックを持たず、グローバル書込ロックも保持しません。低速回線・同時再生の実測結果を残します。

初期版では公開メタデータ・画像・音源・プレビューに `Cache-Control: no-store` を基本設定とし、非公開確認を迂回する共有キャッシュやService Workerのオフラインキャッシュを入れません。区間ループ用に既に読み込んだAudioBufferを端末メモリに保持することとは区別します。

コンテンツハッシュ付きのアプリ用JS/CSSはキャッシュ可能です。将来の素材キャッシュ最適化は、取り下げ確認前のキャッシュ応答を防ぐ方法・無効化・反映遅延を明文化し、別途検証してから行います。

公開版更新で旧Assetが利用できなくなった場合、プレーヤーは失敗を表示して公開情報を再取得し、現在の有効な情報に戻れるようにします。無限再試行や、別の曲への無言の差し替えをしません。

### 11.4 Workersを呼ばないための禁止事項

公開アプリからの `/api/session`、ログイン状態確認、管理ナビの事前fetch、control-planeの画像最適化、再生許可取得、定期的な再生位置送信、Workersへの解析beaconを入れません。公開ページの初回ロードや共有URLの直開きにGitHubログインは不要です。

管理画面への通常のリンクは配置可能ですが、押される前にprefetchしません。管理用コード・Secret・D1 binding・内部DTOを公開bundleへ混入させないでください。

作品URL・曲URLの直開きとブラウザーの戻る/進むに対応します。SPA fallbackはmedia/PHP/APIの404までHTMLへ置き換えないようにし、サブディレクトリ配置時のBASE_URLも設定で扱います。

## 12. DNS・サーバー環境・運用コスト

実際のドメイン・契約プランは未確定です。既存のレンタルサーバーを前提に、設定例と検証手順を用意し、未確認の値を本番値として埋め込まないでください。

公開Music用ホストをレンタルサーバーへ向け、control-planeは既存のホストを維持する案を基本にします。公開ホストをCloudflareで管理する場合はDNS onlyを初期案とし、Workers Routeや音源のCloudflareプロキシ通過を前提にしません。DNS onlyではHTTPをCloudflareのプロキシに通さないため、レンタルサーバー側のHTTPSを用意します。[R12]

PHPの対応バージョン・必要拡張、書き込み可能領域、document root外への保存、ファイルロック、同一ファイルシステム内の置換、本文・アップロード容量、実行時間、ストリーム転送、rewrite、Range、ディスク残量を確認項目にします。秘密情報を表示する公開 `phpinfo()` を置きっぱなしにしません。

Cloudflare側は管理操作中心になりますが、既存control-planeとの合計CPU時間・リクエスト・DB操作は測定します。Workerの共有によって無料枠が新しく増えるとは扱いません。[R4]

レンタルサーバーのCPU・同時接続・転送量・保存容量に負担が移るため、無制限配信を保証しません。通常アクセスがCloudflareへ課金されないことだけを、サイト全体が永久無料である説明に置き換えないでください。

## 13. 調整値・設定・機能フラグ

元指示書の「ドメインの値を変更すれば調整しやすい」設計を維持します。

| 設定の種類 | 置き場所と注意 |
|---|---|
| 音源・画像の投稿上限、最低ループ長 | 型付きのDomain Policyに集約し、外側から注入 |
| 曲順、画像、ループ開始・終了、クレジット | 管理画面で編集するD1の値。公開操作で反映 |
| 署名の許容時間、通信timeout、同時upload数 | Integration/Runtime設定。Domainへ通信方式を埋め込まない |
| Web Audioのデコード予算・試聴位置 | Player Runtime設定。元の予算・解放ルールを維持 |
| PHP保存先・接続先・署名鍵・環境区別 | 非公開の環境設定。秘密をクライアントへ公開しない |
| 広告ON/OFF | Music運営が設定し、公開データへ反映 |
| 色・余白・操作サイズ | Design Tokens |

初期案は音源64MiB、画像8MiB、最大音源長600秒、最低ループ長0.1秒、デコード予算96MiB、同時デコード1です。実際に対応可能な値を測定し、変更した場合は理由を記録します。通信・CPU上限をこの数値だけで保証しません。

TypeScriptとPHPで投稿制約を別々に手入力して値を食い違わせないでください。非秘密の版付きポリシーファイルを生成する、または共通fixtureで一致を検証する方法を採ります。PHPはブラウザーから渡された制約値を信用せず、配置済みの設定を使用します。

`MUSIC_ENABLED`、`MUSIC_PUBLISH_ENABLED` 等のフラグを用意し、既存ゲームの `STAGING_DISPATCH_ENABLED` / `PRODUCTION_DISPATCH_ENABLED` とは分けます。初回の本番設定はMusic無効・公開反映無効を安全な既定値にし、検証してから運営が有効化します。

Music未設定時に、共通モジュールのimportやゲーム画面の描画で例外を発生させないでください。Music専用設定は必要な経路で検証します。ローカルではテスト設定を明示して全機能を動かせるようにします。

## 14. コメント規則【必須・PHPも対象】

意味のある処理ブロックごとに、目的・理由・注意点を日本語の `//` コメントで説明します。TypeScript/JavaScript/PHPの自作関数・メソッド・constructor・Reactコンポーネント・Hook・運用スクリプト・テストヘルパーには、Doxygen風の `/** ... */` コメントを付けます。

TypeScriptは `@brief` / `@param` / `@returns`、PHPはPHPDocとも整合する `@brief` / `@param` / `@return` を基本とし、必要なら `@throws`、副作用、単位、認可の前提、再試行時の性質を記載してください。引数がない関数に架空の `@param` を付けません。

```ts
/**
 * @brief 固定した公開要求をレンタルサーバーへ反映し、確認できた結果を保存する。
 * @param command 対象作品、下書き版、操作IDを含む検証対象の要求。
 * @returns 実際に確認できた反映状態。応答消失時は結果不明を含む。
 * @throws AuthorizationError 対象作品を公開する権限がない場合。
 */
```

```php
/**
 * @brief 現在の公開版で利用が認められている素材を取得する。
 * @param string $assetId サーバー発行の素材ID。
 * @param array $snapshot この要求内で読み込んだ公開スナップショット。
 * @return array 検証済みの素材情報。実ファイルはここでは送信しない。
 * @throws AssetNotPublicException 一般向け配信が許可されていない場合。
 */
```

ブロックコメント例：`// 非公開化後に304で古い素材を再利用させないよう、条件付き応答より先に公開可否を確認する。`

JSX、CSS、SQL、設定ファイルでは有効なコメント構文を使います。既存の無関係な全ファイルへ機械的にコメントを追加するのではなく、今回の新規・変更コードで徹底します。既存機能の大規模整形で差分を埋めないでください。

## 15. API境界の目安

URL名は既存方針に合わせて変更可能ですが、ゲーム管理APIへ混在させません。

| 境界 | 操作例 | 必須認可 |
|---|---|---|
| control-plane `/api/music/games` | 担当作品の取得、作品作成 | 取得は担当範囲、作成はMusic運営 |
| control-plane `/api/music/games/{id}` | 作品編集、曲順、担当者管理 | 編集は担当者、担当変更はMusic運営 |
| control-plane `/api/music/tracks` | 曲登録・下書き編集・ループ設定 | 対象作品の担当者 |
| control-plane `/api/music/assets` | upload開始・転送・確定・プレビュー | 対象作品の担当者 |
| control-plane `/api/music/publications` | 公開・非公開・状態確認・再試行 | 対象作品の担当者。全体停止等はMusic運営 |
| control-plane `/api/music/settings/ads` | バナー・広告表示設定 | Music運営のみ |
| PHP管理bridge | 素材操作・公開反映・状態照会 | 正しい用途限定署名と対象整合性 |
| PHP公開catalog/media | 公開データと公開Asset | ログイン不要。ローカルの現在版に含まれるものだけ |

401/403/404/409/413/429、外部通信障害、結果不明を区別し、内部path・SQL・Secretを返さないでください。表示ボタンを隠すだけではなく、各サーバー入口で検証します。

## 16. テストと受け入れ条件

元指示書の音声・スマホ・公開・広告・コメントのテストに、次を追加します。

| ID | 試験 | 合格条件 |
|---|---|---|
| R-01 | 既存ゲームのログイン・権限 | 従来の許可・拒否条件を維持し、既存の正規ユーザーが利用できる |
| R-02 | 既存Intake / uploader / Actions | 既存の認証・アップロード・実行条件を保持。外部実行はモック等で安全に検証 |
| R-03 | Production承認 | Music追加後も既存ゲームの別人承認・環境条件を省略できない |
| R-04 | Musicのみの担当者 | リポジトリ書込権限なしで担当OSTを管理でき、ゲームAPI・ゲームデータへアクセスできない |
| R-05 | 権限なしのGitHubユーザー | 自動でMusic権限を取得せず、管理操作・管理データ取得を拒否 |
| R-06 | ゲーム権限のみのユーザー | Music割り当てがなければMusic管理を拒否 |
| R-07 | 作品境界 | 別作品の曲・Asset・公開操作IDを指定しても読取・変更・公開できない |
| R-08 | 権限失効 | Cookieが残っていても、担当解除後の次の管理操作を拒否 |
| R-09 | Music未設定・OFF | 既存ゲーム画面・APIが動作。新機能のSecret不足で共通処理が停止しない |
| P-01 | 公開サイトの独立 | control-planeを停止・通信遮断した状態で、公開サイトを再読み込みし、作品移動・画像表示・再生できる |
| P-02 | 通常時の通信 | 初回表示、曲URL直開き、再生、シーク、曲送り、区間ループでWorkersへの要求が0件 |
| P-03 | ループ | 対応音源でイントロ1回＋10周以上。ループごとに音源を再取得しない |
| P-04 | スマホ | iOS Safari / Android Chromeを対象にする。実機未実施は未検証と明記 |
| P-05 | Range / HEAD | 公開状態確認、byte範囲、status、各Contentヘッダー、本文長が正しい |
| S-01 | 下書き保護 | 実ファイルURL、保存領域、過去snapshot、管理previewを未認証で取得できない |
| S-02 | 非公開化 | 完了後の新しいcatalog、media GET/HEAD/Range、画像、旧IDに非公開内容を返さない |
| S-03 | キャッシュ迂回 | 条件付き要求やキャッシュ経由で取り下げ後の内容を返さない |
| S-04 | 署名 | 改ざん、期限切れ、未来日時、nonce再利用、別環境・path・作品への転用を拒否 |
| S-05 | upload検証 | 偽MIME、上限超過、途中切断、不正path、実行ファイル、別作品ID、確定済み上書きを拒否 |
| S-06 | 秘密 | 公開bundle、公開JSON、ログ、エラー、GitにSecret・Cookie・内部パスを含めない |
| C-01 | 公開版の維持 | 下書き編集中・転送中・検証失敗中は、以前の公開版を維持 |
| C-02 | 複数担当者の編集 | 同一リビジョンの競合を検知し、他人の変更を無言で消さない |
| C-03 | 複数作品の公開 | A/B同時更新で、他作品の公開内容・広告が巻き戻らない |
| C-04 | 障害注入 | 送信前、切替前、切替直後、receipt前、D1確認前で停止し、状態を正しく再照合できる |
| C-05 | 冪等性 | 同じoperation ID・同じ内容の再試行で二重処理せず、別内容は拒否 |
| C-06 | 遅延した要求 | 後から届いた古い公開要求が、最新の公開・非公開化を上書きしない |
| C-07 | 残骸回収 | 一時ファイルは整理でき、参照中・保留中・必要な復旧用素材を削除しない |
| A-01 | 広告 | Music運営だけが設定でき、公開サイトはローカル設定で表示。OFF・失敗でも再生が動く |
| D-01 | 設計とコメント | Domainの外部依存を検査。新規TS/PHPの関数・処理ブロックに規定コメントがある |

P-01/P-02は「Workersをモックに差し替えたから動く」ではなく、公開経路に管理サービスへの依存がないことを確認します。ブラウザーのリクエスト記録と公開ビルドの依存検査を残してください。

PHPの組み込み開発サーバーだけでは、本番のrewrite・アクセス拒否・同時実行を保証できません。可能なら本番に近いHTTP環境で自動検証し、実契約サーバー固有の確認は別の手動チェックリストにします。

iPhoneの画面サイズエミュレーションを実機の音声・画面ロック試験と同一視しません。音楽がバックグラウンドで必ず続くとは、未検証のまま保証しないでください。

## 17. 実装の進め方

1. **既存調査・基準点**：ブランチ、未コミット変更、instructions、既存認証・権限・DB・API・テストを確認し、変更前の結果を記録する。
2. **境界と回帰試験**：Music専用ユーザーとゲーム専用ユーザーのケースを先に追加し、共通本人確認とサービス別認可を分離する。
3. **Musicの骨格**：無効フラグ、管理画面入口、Music用Domain/Application、追加migrationを作る。既存ゲーム機能を継続確認する。
4. **PHPと契約**：私有保存、署名検証、upload、preview、公開snapshot、操作receipt、Range配信をローカルで実装する。
5. **最小の一貫動作**：1作品1曲についてcontrol-planeで登録・公開し、レンタルサーバーの公開アプリから聴けるようにする。
6. **残る初期機能**：2作品5〜10曲、曲別画像、ループ設定・試聴、共同編集、更新・取り下げ、広告へ広げる。
7. **障害・安全性**：競合、再試行、通信遮断、非公開URL、キャッシュ、署名改ざん、既存ゲームへの権限越境を検証する。
8. **配布準備**：静的アプリとPHPの配置物、migration、設定例、バックアップ・復元、切り戻し、未設定事項をまとめる。

既に独立したMusic実装がある場合は、UI・プレーヤー・純粋ドメインを優先して再利用します。Music用R2等が既に作成されていても、内容を調査せず削除しません。移行は対応表・検証・復旧方法を用意してから行います。

既存ゲームを止める一括置き換え、production DBへの試し書き、実公開Actionsの動作確認目的の起動は行わないでください。

Musicに対する新しい設定不足で既存Worker全体をデプロイ不能にしないでください。外部デプロイは承認待ちとして準備まで行い、実行していないデプロイ・ブラウザー試験・広告サービス接続を完了扱いにしません。

## 19. 最終報告の形式

実装の最後に、次を区別して報告してください。

1. 実装したMusic機能と、既存から再利用した部分。
2. 変更した既存認証・権限・API・DBと、既存ゲームへの影響確認。
3. 公開サイトがWorkersへ通信しないことの検証結果。
4. PHPの署名・素材・公開同期・取り下げ・再試行のテスト結果。
5. スマホ通常再生・区間ループの実測、実機未検証の項目。
6. ローカル起動、本番配置、必要な設定、利用者が行う外部設定。
7. 完了・未完了・外部設定待ち・未検証。無料枠や配信負荷についての測定と仮定。

**今回の完成ラインは「担当者が既存control-planeからOSTを登録・自主公開し、一般の人がWorkersを呼ばずにレンタルサーバーのMusicサイトで画像付き再生と区間ループを楽しめる。しかも既存のゲーム公開機能と権限が壊れていない」ことです。**
