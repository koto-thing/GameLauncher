# LT会の半自動運営

## 第1段階: 自動承認と発表枠の割り当て

- 新規開催回の承認方式は自動承認を初期値とし、開催設定から手動承認を選択可能
- 募集期間内・公開中・開催前・空き枠ありの初回申請は、受付と同じトランザクションで承認、枠確保、時間割追加、公開版生成、通知予約まで確定
- 発表時刻はサーバーで現在の時間割末尾から算出し、共通発表時間と転換時間を適用
- 閉会がある場合は直前へ追加し、閉会の長さを維持して後ろへ移動
- 0分転換も明示的な転換枠として保持
- 自動承認では承認通知だけを予約し、手動承認では受付通知と後日の承認通知を別々に予約
- 差し戻し後の再提出は手動確認を維持し、再承認まで旧公開版を保持
- 承認方式の切替は新しい申請に適用し、既存の審査待ちは自動公開しない
- 開催回コピーは承認方式も引き継ぎ、従来どおり日時確定までは非公開

申請の重複や満枠では申請・公開版・通知の部分成功を残さない。同一operationIdの再送は保存済み結果を返す。自動承認の監査主体は `system:auto-approval` とし、本人の操作IDと内部承認IDを分離する。

共有契約の `EventSettings`、`CreateEventInput`、`UpdateEventInput.data` には `approvalMode: automatic | manual` を必須とする。旧形式へのフォールバックは設けない。DB定義は `0042_automatic_approval.sql` で更新し、APIと管理画面を同じ変更として配布する。

## 次の実装順

1. 開会・休憩・閉会の時間割ルールと自動生成
2. 開始日時・共通時間の変更に連動した全体再計算
3. 終了上限と募集可能枠数の計算

これら3点は第1段階には含まない。現在は設定済みの発表時間・転換時間と手動追加した開会・休憩・閉会を利用する。

## 検証

`services/lt-api/tests/automatic_approval_runtime_test.py` を通常のruntime runnerへ追加。初回公開、同一操作の再送、最後の1枠への同時申請、閉会前への追加、0分転換、再提出の手動確認、承認方式切替を実Worker/D1で検証する。
