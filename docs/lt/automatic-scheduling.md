# LT会の半自動運営

## 第1段階: 自動承認と発表枠の割り当て

- 新規開催回の承認方式は自動承認を初期値とし、開催設定から手動承認を選択可能
- 募集期間内・公開中・開催前・空き枠ありの初回申請は、受付と同じトランザクションで承認、枠確保、時間割追加、公開版生成、通知予約まで確定
- 発表時刻はサーバーで現在の時間割末尾から算出し、共通発表時間と転換時間を適用
- 閉会がある場合は直前へ追加し、閉会の長さを維持して後ろへ移動
- 0分転換も明示的な転換枠として保持
- 自動承認では承認通知だけを予約し、手動承認では受付通知と後日の承認通知を別々に予約
- 差し戻し後の再提出は手動確認を維持し、再承認まで旧公開版を保持
- 承認方式の切替は新しい申請に適用し、既存の審査待ちは自動公開しない
- 開催回コピーは承認方式も引き継ぎ、従来どおり日時確定までは非公開

申請の重複や満枠では申請・公開版・通知の部分成功を残さない。同一operationIdの再送は保存済み結果を返す。自動承認の監査主体は `system:auto-approval` とし、本人の操作IDと内部承認IDを分離する。

共有契約の `EventSettings`、`CreateEventInput`、`UpdateEventInput.data` には `approvalMode: automatic | manual` を必須とする。旧形式へのフォールバックは設けない。DB定義は `0042_automatic_approval.sql` で更新し、APIと管理画面を同じ変更として配布する。

## 第2段階: 時間割ルール・再計算・終了上限

- 新規開催回は時間割も自動生成が初期値。手動編集方式を選択可能
- 開会5分、4発表ごとに休憩10分、閉会5分を初期値とし、開催回ごとに変更可能
- 開会・休憩・閉会は0分で省略可能。最後の発表後は休憩を挟まず、転換と閉会を確保
- 初回申請の自動承認と運営による手動承認は、閉会前へ追加した後でルールから再生成。管理画面では自動時間割の手動承認に時刻入力は不要
- 自動時間割の編集画面では発表順を変更し、保存時に補助枠と時刻を計算
- 開催前の開始日時・発表時間・転換時間・ルールの変更では、発表順を保持して全体を再配置。手動方式では補助枠の長さと順番を保持
- 開催前の辞退確定時も再計算し、不要になった休憩を削除。開始後の辞退では予定時刻を維持
- 設定保存後は管理画面の時間割と申請一覧も再取得し、公開ページ・公開発表と同じ時刻を表示
- 開始後・終了後の時間基準やルール変更は拒否

自動方式では終了上限を任意指定できる。指定時の募集可能数は、開会・発表・各転換・途中休憩・閉会を含め、上限に収まる最大件数としてサーバーで確定する。例として発表10分・転換1分・上記初期ルールでは75分に5件が収まる。上限なしでは定員を手動指定する。手動時間割方式へ切り替える際は終了上限を解除する。

上限が1件も収容できない場合、予約済み発表を収容できない設定変更、上限まで満枠の申請は拒否する。時刻や発表時間を自動短縮しない。設定・時間割・公開版・通知を同じトランザクションに含め、超過時は部分変更を残さない。管理画面は理由を表示し、そのまま設定を調整して再保存できる。

共有契約の開催設定に `scheduleMode`、`openingMinutes`、`breakEvery`、`breakMinutes`、`closingMinutes`、`endsBy` を必須追加。`endsBy` は上限なしの場合も `null` を明示する。DB定義は `0043_schedule_rules.sql`、上限超過の契約エラーは `SCHEDULE_FULL`。API・共有契約・管理画面を合わせて配布する。

## 検証

`services/lt-api/tests/automatic_approval_runtime_test.py` を通常のruntime runnerへ追加。初回公開、同一操作の再送、最後の1枠への同時申請、閉会前への追加、0分転換、再提出の手動確認、承認方式切替を実Worker/D1で検証する。

`services/lt-api/tests/schedule_rules_runtime_test.py` は実Worker/D1で、休憩境界、上限からの定員計算、超過時のロールバック、並び替えと再送、取り下げ後の休憩削除、設定変更と公開時刻の同期、設定コピー、開始後の変更拒否、手動承認の生成後時刻を検証する。容量計算の境界はRust単体試験でも確認する。
