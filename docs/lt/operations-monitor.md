# 運営通知と稼働確認

管理画面 `/lt` の「自動運営と通知」で、全開催回の辞退依頼、空き枠があるキャンセル待ち、資料期限超過を確認する。終了・中止・辞退確定・確認済みの対象は現在状態から除外する。対象を押すと開催回または申請を開く。

## 本人の通知設定

- 初期状態は無効。「このブラウザーで通知を有効にする」を押したときだけブラウザーの通知許可を求める
- ユーザー単位の同意と端末単位の購読を管理DBに保存する。別端末でも受信する場合は、その端末で登録する
- 「自分の全端末で通知を停止」で本人の購読をすべて削除する。再開時は各端末で登録し直す
- 運営権限・在籍バージョンを配信前に確認し、権限取り消しや再承認後に古い購読を復活させない
- 通知は画面を閉じていてもブラウザーのプッシュ機能で届く。ブラウザー・OSの通知設定やバックグラウンド動作設定によって表示が制限される場合がある
- 通知文には申請内容・メールアドレス・開催名を含めない。クリック後の管理画面には通常ログインが必要

## 稼働表示

LT APIの毎分cronだけが `lt_maintenance_status` を更新する。5分以上成功記録がない場合、明示停止設定、直近失敗を区別する。管理画面を開いても稼働記録は更新しない。メールの停止・試験宛先限定・送信待ち・15分以上の遅延・失敗・結果不明も表示する。送信結果不明は自動再送しない。

管理Workerの5分ごとのcronは内部RPCから状態を取得し、要対応識別子が変化した購読に通知する。同一状態を繰り返し送らず、解消だけで対象がゼロになった場合は通知せず記録を更新する。ブラウザーの通知tagでも重複を集約する。1回最大10端末を処理し、一時失敗は5分後、失効購読は削除する。管理Worker自身の停止は画面上の最終確認時刻から15分で判定する。

## 配備

1. LT専用D1へ `0042`～`0044` の未適用スキーマを適用する。管理D1には `0008_lt_push.sql` を適用する
2. 管理Workerのsecret `LT_PUSH_PUBLIC_KEY` と `LT_PUSH_PRIVATE_KEY` に専用P-256 VAPID鍵を設定する。秘密鍵をGit・ログへ書き込まない
3. LT APIのproduction-apiビルド、公開LTサイト、管理Workerを配備する。管理Workerの `LT_INTERNAL` は既存 `pandd-lt-api#LtOperator` を使う
4. 管理Workerのcronは5分ごとの1件にまとめる。通知は毎回、既存の保持処理は日本時間03:00だけ実行し、無料枠のアカウント全体5件を超えない。LTの保持削除設定は変更しない
5. 稼働記録の更新、未認証APIの拒否、service worker配信を確認する。利用者の通知許可は本人が管理画面から行う

暗号化とVAPID署名には [webcrypto-web-push](https://github.com/block65/webcrypto-web-push) を使用する。購読先はChrome・Firefox・Edge・Safariのプッシュサービスに限定し、外部リダイレクトは追従しない。

## 検証

`monitor_runtime_test.py` で実Worker/D1の要対応判定と公開経路の拒否を確認する。管理側の `lt-push.test.mjs` は実SQL・実暗号化で重複、受信停止、権限取り消し、購読失効、再試行を検証する。`lt-notification-settings.test.mjs` は署名セッション、Origin、本人境界を確認する。ブラウザーの購読APIを隔離した `lt-monitor.browser.mjs` では明示同意・停止・画面遷移と幅390/1280pxを確認する。実端末の通知到着確認は本人のオプトイン後に行う。
