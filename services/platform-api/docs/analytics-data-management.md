# 統計負荷とデータ管理

2026-10-15、既定ブランチ `master` の `54c46775`（PR104反映済み）を調査。
保存方針維持とPR・マージ・配備のユーザー承認済み。既存90日/365日処理を維持する。
契約、認証・権限、削除対象を変更せず、手動cleanupは実行しない。

## 現状と変更理由

統計は `services/platform-api` の専用Worker/D1。Admin Webの統計画面からService Bindingで呼ぶ。
送信は同意後のみ、ランダムなインストールIDと資格情報ダイジェストを使い、IPやハードウェアIDは保存しない。
既存の `analytics_daily` は90日を過ぎたセッションを匿名集計するもの。直近90日の中央値・端末数・再訪率は
詳細SQLから取得するため、画面の再読込ごとに再計算していた。

Admin Webは既存 `audit_events`（公開処理等、ハッシュ連鎖）、`operation_events`（ロール・招待・拒否等）、
`music_audit_log`（Music操作）を使う。新しい監査ストアや利用者識別子は追加しない。
誰が・いつ・何を変更したかは既存actor、action/event_type、target/payload、時刻に残す。
ハッシュ連鎖は外部アンカーのない整合性確認であり、DB管理者による書き換えを完全に防ぐ仕組みではない。

今回の変更:

- 認証と入力検証後に、DB・環境・期間・作品・版ごとに60秒キャッシュ。1 isolateにつき16件、直列化後合計4 MiBまで
- 同じ条件の同時要求は1回にまとめる。別条件の集計が実行中なら503。失敗後30秒は新しい集計を抑止
- キャッシュはトークン、IP、SQL、インストールIDを含まない集計だけ。ブラウザーへの `no-store` は維持
- 削除API成功後は当該isolateのキャッシュを破棄。削除と競合した古い集計をキャッシュへ戻さない
- Admin Webは応答本文を含め5秒で待機終了し、統計だけのエラーを返す。D1実行そのものの中断は保証しない
- オプションのD1診断と全体集計時間を追加。診断失敗はDB操作の成功を変えない
- 日別集計と日別詳細の期間検索に索引を追加するSQLを準備。本番適用は別承認
- 統計・申請履歴のCronは明示したactive設定で既存90日/365日処理を維持。disabled/dry-runも選択可能

キャッシュはisolateごとであり全世界共通ではない。別isolateでは削除前の匿名集計が最大60秒残り得る。
新規送信はキャッシュを毎回無効化しないため、反映にも最大60秒の遅れがある。キャッシュは再起動で失われる。
初回の大きな集計、複数isolate、別条件の連続検索には読み取りが発生する。厳密なアカウント予算制御ではない。
中央値や期間内ユニーク数は日別値の単純合計では代替できないため、指標の定義を変えていない。

## 保存先の台帳

| データ | 現在の保存先・責務 | 方針 |
| --- | --- | --- |
| 作品・版・権限・運営招待・公開状態 | Admin Web D1 `pandd-deployment-control-plane` | メタデータのみ。資格情報は既存の秘密設定を維持 |
| 受付ゲームZIP | 既存R2 `pandd-launcher-intake`、D1にはキー・サイズ・digest | バイナリをDBへ入れない。参照中ZIPを削除しない |
| 公開ゲーム・画像・manifest | 既存publisherの配信先・署名manifest | 公開処理や既存ファイルを移動・変更しない |
| Music作品・素材参照・公開処理・監査 | 同じAdmin Web D1の `music_*` | 音源や画像本体は保存しない |
| Music音源・画像・公開snapshot | 既存レンタルサーバーの私有ファイル領域 | 公開閲覧・再生はWorkers/D1への依存なし |
| 同意済みプレイ詳細・匿名日別集計 | `pandd-play-analytics` / `pandd-play-analytics-staging` | メタデータと数値のみ。端末IDを管理画面へ返さない |
| Docs編集・セッション・監査 | `pandd-docs` D1 | 統計とは別用途。既存の期限・認証清掃はこの変更の対象外 |

Music管理は共通D1を使用するため、アカウント上限到達時には管理・公開が影響を受け得る。
ゲーム配布・Music公開再生の既存ファイル経路と、統計APIの障害は分離されている。
Admin/幹部/幹部補佐の既存認可と、全作品公開可能という仕様は変更しない。

収集項目は既存契約の用途に限定する。ランダムIDと資格情報ダイジェストは再送の所有権確認・本人削除、
session/revisionは重複排除、作品/版/環境は比較、開始/最終観測/終了/日別時間は期間集計・中断判定、
outcome/exitCode/crashedは終了結果とスナップショットの整合性確認に使用する。
launcherVersionは同一セッションの属性変更検出にも使われる。これらの既存項目は破壊的に削除しない。
名前、メール、行動イベント列、キー入力、GPS、IPの永続記録や追加の追跡IDは導入しない。
IPは既存レート制限の入力にのみ使う。今後項目を廃止する場合は契約・クライアント・検証処理を一緒に見直す。

## DB別の観測と全体の無料枠

Cloudflare公式資料では、Workers FreeのD1はアカウント全体で500万rows read/日、10万rows written/日、
保存合計5 GB。日次上限はUTC 00:00に更新される。同一アカウントでDBを増やしても枠は増えず、
上限到達は共通D1を使う公開操作にも波及し得る。SQLの返却行数と実際の走査行数は別物。

確認先:
- [D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/)
- [D1 Metrics and analytics](https://developers.cloudflare.com/d1/observability/metrics-analytics/)

CloudflareダッシュボードのD1 Metricsで上記4 DBを個別に確認し、同じアカウントの他DBも合計する。
`scripts/d1-usage.graphql` は一日のUTC日付をstart/endに指定して全DBの行数・クエリー数・p90時間を取得する
読み取り専用クエリーの準備物。アプリDBの全件SQLは実行しない。GraphQLのエラー率を推測で作らない。
保存済みGraphQL応答は次でローカル一覧化できる:

```powershell
node scripts/d1-usage-report.mjs metrics.json 2026-10-15
node scripts/d1-usage-report.mjs metrics.json 2026-10-15 events.jsonl
```

`events.jsonl` は後述の診断JSONを1行1イベントにしたファイル。同じ観測期間を使用する。
件数・エラー件数・実測p95を表示するが、サンプリングや未収集部分を含む全体のエラー率とは扱わない。
GraphQL応答が欠損・エラー・異なる日付・取得上限なら成功表示しない。現在時点の使用量は取得していない。
GraphQLの実行検証には対象アカウントのAnalytics読み取り権限が必要。この作業で資格情報を作成・取得していない。
既存の認可済み手段がない場合、API接続は未完了。ダッシュボード確認は別の選択肢になる。

`D1_METRICS_ENABLED="true"` を承認された検証環境で明示すると、Platform APIとAdmin Webで以下を出力する:

| イベント | 内容 |
| --- | --- |
| `d1_operation` | 固定DBラベル、操作種別、成功/失敗、`rowsRead` / `rowsWritten` / D1時間 / 待機時間 |
| `analytics_report` | 固定DBラベル、成功/失敗、時間、source（database/cache/coalesced/rejected） |

SQL、検索条件、IP、トークン、ユーザー/端末ID、例外本文は出さない。追加DB書き込みなし。
source別にp95を分け、キャッシュ応答が多数あっても遅いDB再集計を隠さない。
`first()` / `raw()` や例外にはD1メタデータがないため行数はnull。全体枠はCloudflareのメトリクスで判断する。
Docsの操作ログ計測は追加していない。Docsも含むDB別の使用量・時間はGraphQL/ダッシュボードで見る。
本番の診断フラグはfalse、Platform APIのobservabilityもfalseのまま。新たな監視の本番有効化は行わない。

通知対象・しきい値の**提案**（未設定、実送信なし）:

| 条件 | 対象と対応案 |
| --- | --- |
| アカウント日次枠の50% | 運営担当が内訳・残時間を確認 |
| 70%または当日枠超過の見込み | 運営担当が統計読み取り停止を判断、管理・公開の余力を確保 |
| 85%またはD1 quotaエラー | Adminへ連絡する運用案。統計収集停止も検討 |
| 統計p95 > 2秒、5分内エラー > 5%かつ20要求以上 | 統計担当が条件・索引・障害を確認 |

これらは余力を保証しない。収集が多ければ書き込み枠にも注意する。外部通知先や自動停止は実装しない。

## 保存方針と非破壊プレビュー

統計詳細90日→匿名日別集計を保持、申請履歴365日の既存方針はユーザー承認済み。
下表の30日・24か月等は将来の代案であり今回適用しない。

| データ | 既存実装 | 推奨案・影響（承認待ち） |
| --- | --- | --- |
| プレイ詳細 | 90 JST日、過去分を日別匿名集計後に削除 | まず既存90日を候補にする。30日案なら識別可能データが減るが中央値・再訪率の比較期間も短くなる |
| 匿名日別集計 | 無期限 | 年次比較に必要な期間を決める。暫定候補24か月。自動削除しない |
| 失効ダイジェスト | 削除後90日 | 再送で復活しないため既存期間維持を推奨。短縮はクライアント再送範囲と同時検討 |
| 公開申請と関連監査 | 完了等から365日相当、更新・参照元保護あり | 365日案を運営確認。障害調査・復旧証跡を失うため削除前に参照と保全を確認 |
| グローバル監査・運営変更・Music監査 | 自動削除対象外 | 最低1年等を運営が決定するまで保全。別の削除経路を追加しない |
| 素材ZIP・画像・音源 | 既存ストレージと参照情報 | 一律期限を付けず、公開/復旧参照とバックアップを確認して個別判断 |

デプロイ設定の `ANALYTICS_RETENTION_MODE` と `REQUEST_RETENTION_MODE` は `active`。
activeはそれぞれ既存 `archiveDetails` / `pruneRequestHistory` を同じ期限・対象・Cron時刻で呼ぶ。
停止は `disabled`、非破壊確認は `dry-run`。設定欠落・誤字・`enabled`・`delete` ではDBアクセスしない。
統計dry-runは既存索引で期限前の候補を最大101件調べ、候補100件とそれ以上の有無を返す。
申請dry-runは期限前の最古100件だけを確認し、完了・監査更新・実行更新・参照保護条件に合う件数を返す。
全件数ではない。対象の関連履歴を確認する読み取りは発生するので本番実行も別途判断する。
Cronで明示実行したdry-runの結果は識別子を含まないJSONで出力する。

既存 `archiveDetails` / `pruneRequestHistory` の変換・削除ロジックを再利用し、新しい削除対象やHTTP削除入口は追加しない。
アーカイブ成功後は当該isolateの集計キャッシュも無効化する。
既存の利用者本人の削除APIは維持し、収集停止中も受け付ける。

既存処理は対象全体を同一トランザクションで扱うため、将来データ量が増えた場合のバッチ上限・再開位置は別途検討する。
今回の配備では既存処理の即時起動・手動cleanupを行わず、従来のCron時刻を維持する。
停止を選択した場合は詳細/履歴が増え続けるため容量・読み取り増加に注意する。

## 承認後に行う手順案

1. 日次枠とDBサイズの証拠をダッシュボード/メトリクスで確認。生ログの全件COUNTを避ける
2. 保存期間と対象、監査・公開/復旧参照の保全方針、削除実行者を承認する
3. ローカルまたは検証コピーでdry-runし、バックアップ・復元可否と処理件数を確認する
4. 索引追加も行読み取り/書き込み・容量を使うため別承認で計画適用。Workerは新索引なしでも正しく動く
5. 将来削除を有効にする際は件数上限・再開位置・再実行/同時更新を検証し、既存の監査へ実行者・対象・cutoff・結果を記録する
6. ストレージ実体の削除はDB保存方針と分離。公開・復旧参照、Music snapshot、ハッシュを照合した承認済み対象だけに限定する

配備結果・バージョンは作業報告に記録する。GraphQL実接続や外部通知の稼働はこの変更に含まない。
